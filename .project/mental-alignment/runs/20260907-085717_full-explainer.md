# Feedback before building

## TLDR

- Building fusion hardware is slow and expensive, so the 1cFE project asks how much useful feedback an engineer can get before building. This work is a concrete test of that question on one stellarator design.
  - The 1cFE survey of 38 fusion concepts gave rough costs. The next question is "what would have to be true for 1 cent per kWh?" That needs a model that connects physics to cost and carries, for every design point, a pass/fail verdict on each asserted limit, so a design that is not physical reads violated.
  - The team's existing cost tool, 1costingFE, fixes at design time which quantities are inputs and which are solved for. Here the model is plain text, every calculation runs forward from design choices, and viability is checked, not solved for. Any quantity can be swept; nothing can be solved for. That is a trade, and the explainer says so.
- Four repositories share one loop: get evidence from sources, write it into a text model, compile the model into runnable code, run thousands of design points, read what the checks say, and change the model where it was wrong.
  - agentic-mbse turns PDFs into cited insights and validates the text model. sysml-codegen compiles the text model into a Python package. teax runs that package and records pass/fail verdicts. fusion-tea holds the fusion models, the studies, and the rules that tie the loop together.
  - Scale today: 25 model files (6,811 lines, 57 calculations, 11 limits), one generated package of 81 modules with 205 inputs, nine committed studies of about 30,000 design points, nine goals, 33 completed model changes, 10 recorded architecture decisions.
- The compiled model is a one-way calculation graph with no loops. That is why it is fast and auditable, and it is why some physics has to be reshaped before it fits.
  - A quantity that really is a loop (the plasma's heating balance) is solved inside one hand-written calculation and then checked by an inequality, never solved across modules. Three of 60 calculation implementations are hand-written; 57 are compiled from the text.
- The system's main job is catching its own mistakes, because the failure mode of a naive sweep is a smooth, plausible, wrong map.
  - Every number cites a page. An independent hand-written check re-derives every formula to one part in a billion. A model change becomes usable only after a checking script proves that the committed, compiled package is exactly what the model text says, and stamps that version with a fingerprint. A fresh session that did not do the work reviews every study reading and every round.
  - It works. Between the first study (2026-08-21) and today (2026-09-07) the loop found a pumping power 100× low, a wall-load check comparing an average to a peak limit, a stored energy 6% high, and a heating check that passed plasmas the heating system could not hold. Each fix landed as a cited model change, and the next study re-ran the affected design points against the new, proven package version.
- A goal is a grounded question pursued one bounded task at a time, with the next task chosen from evidence. The current goal, burn-control, is a real end-to-end instance.
  - Two words carry the finding. A driven plasma needs some auxiliary heating to stay where it is; an ignited plasma heats itself from its own fusion and needs none. The verdicts now say the machine as designed is a driven operating point with 0.92 MW of heating margin, and that most of the "feasible" points earlier studies reported were ignited plasmas that, in this model, would run away. The cheapest point that passes every verdict is 202 $/MWh, about 20× the target. The value is not the number; it is that the heating check now bounds the design point from both sides (too little installed heating fails one limit, too much self-heating fails the other), and each limit traces to a printed page.
  - What this does not yet show: faster hardware progress, or agreement with an independent design (the ARIES-CS comparison is sealed and planned, not run).

## 1. A limit that fails in the model is feedback you get before you build

The ambition behind everything here is the owner's: "What would it take for us (humanity) to rapidly accelerate real innovation and progress in the world of physical technology?" [OWNER-VERBATIM, `.project/concepts/physical-innovation-narrative.md` § 1]. Hardware still has to be built; software agents will not deliver a reactor by themselves. The leverage is in choosing which concepts to invest in and knowing exactly what a demonstration must prove [OWNER, § 1]. The recurring question is therefore "how much useful feedback can we obtain before building, and how can that feedback make the building count for more?" [AGENT, ratified by owner, § 2].

The 1cFE project gave that question a test. Its first stage surveyed 38 fusion concepts with an automated analysis pipeline and a public score explorer [code: `exploration/concept_analysis/README.md`; `docs/index.html`]. The next stage asks, for one promising concept, "what would need to be true to get to 1c per kWh?" [OWNER-VERBATIM, `.project/concepts/stellarator-mbse-demo.md`]. One cent per kWh is $10/MWh. Answering needs a model that connects plasma physics, magnets, walls and heating to cost, and that asserts limits: at each design point every asserted limit evaluates to satisfied or violated, and the record carries that verdict. The vehicle is Stellaris (concept 09), a quasi-isodynamic stellarator: one whose twisted magnetic field is shaped so that particles do not drift out, which is what lets it run steadily without a plasma current. It was chosen because its design paper prints complete geometry and power tables and no cost data, so the cost side cannot copy the source [AGENT, ratified, same file].

What makes this different from 1costingFE, the team's own costing tool, is the owner's own contrast: a tool like 1costingFE must "decide 'what are the inputs' and 'what gets derived' (which can then be painful to change later)"; this approach "is totally generalized to forward-pass and assess only. Not necessarily 'better', just has its own pros and cons" [OWNER-VERBATIM, same file]. Concretely: 1costingFE's `forward()` solves fusion power backwards from a net-electric target [doc: same file, Key Concept 3]; the SysML model takes every design choice as given, computes everything downstream, and asserts limits as pass/fail verdicts. Any quantity can become a study axis; nothing can be solved for. The machinery was checked against 1costingFE once (the model fed 1costingFE's solved point reproduced its per-account costs; "Anchor A"), then the owner closed that duty: "we showed we could do it. pin it ... I do not want to be anchored to 1costingFE" [OWNER-VERBATIM 2026-08-30, `.project/concepts/stellarator-demo-maturation.md`; pin recorded in `work/orchestration/stale-basis-recompute.md` Addendum]. The stellarator model still cites 1costingFE's cost formulas as its engineering source, by file and line [code: `stellarator_plant.sysml` doc comments].

The technical motif is AI-for-software carried into AI-for-systems [OWNER, narrative § 3]: text models, version control, automated checks and agent workflows transfer. The difference that does not transfer is that a physical model can run perfectly and still be wrong about the world; executing it shows the consequences of its assumptions, and only engineering evidence says whether the assumptions hold [AGENT, § 3]. That is why most of the machinery below is about provenance and independent checking rather than about running fast.

One boundary, stated once: what is demonstrated is that agents can run this loop end to end, catch the model's own errors, and record why. Faster physical innovation is the aspiration the loop is built to test, not a result. The one irreversible external test (comparison against the sealed ARIES-CS study) is planned and has not run [INHERITED: narrative § 4; `epic_stellarator_mbse_demo.md` Item 7].

## 2. The loop runs from a source page to a pass/fail verdict across separate repositories

The loop needs four different kinds of tool, and each lives in its own repository because each is useful without the others [AGENT; the dependency direction is in `sysml-codegen/pyproject.toml` and `docs/integration_seam_operator_guide.md`].

| Repo | Problem it solves | The parts | Size |
|---|---|---|---|
| `~/1cfe/agentic-mbse` | Get engineering evidence out of papers and into a model that cites it; keep the model valid | PDF extraction (`src/agentic_mbse/extraction/pipeline.py`); the modeling project-management layer (`pm/`): recorded insights (filed as DI), promoted requirements (PR), validation rows (SV), work items (WI); six-level SysML validation (`validation/runner.py`); 15 commands, 5 agents, 10 skills symlinked into a project by `agentic-mbse init --dev` | 60 files, 22k lines |
| `~/1cfe/sysml-codegen` | Turn the text model into runnable code: parse and interpret the SysML text; wire definitions to their instances; turn expressions into code; admit hand-written blocks where SysML cannot express the calculation | parse → instance graph → computation graph → Jinja-rendered package; cycle check in `elaboration/graph.py`; sealing and fingerprints in `contracts/seal.py`; CLI `sysml-codegen generate / snapshot / seal` | 72 files, 20k lines, 2,149 tests |
| `~/1cfe/teax` (package `teax-simkit`, import `simkit`) | Run typed pipelines in dependency order; turn asserted limits into three-valued verdicts; run and store studies | `simkit/core` (executor), `simkit/evaluation` (gates → verdicts), `simkit/study` (runner, store, `teax-study` CLI) | 244 files, 25k lines |
| `~/1cfe/fusion-tea` | Hold one concept's cited model, its studies and its goals in one place, and make three separate tools behave as one auditable loop | the models, the generated package, the study records, the goal directories, and the seam scripts; see the map below | 988 commits since 2026-01-05 |

The traceability chain the toolkit enforces, in plain words: a source document → a recorded insight (DI) → a promoted requirement (PR) → a model element whose doc comment cites the source by file and line → a validation row (SV) that checks it [doc: `agentic-mbse/claude/skills/source-traceability/SKILL.md`]. Every quantitative value in the model must carry a citation (requirement MR-4, `modeling_project/REQUIREMENTS.md`).

How an agent session and the programs combine those parts during one investigation (the behavioral view). The agent is a Claude Code session; it reads files, calls each repo's command-line tool or skill, and writes records. Programs hand off through files on disk, never through shared memory, which is what lets a fresh session resume [AGENT; the hand-offs are in `GOAL_RUNBOOK.md`, `run-study/runbook.md`, and the two operator guides under `docs/`]:

1. Question. The operator and a session write `goal.md` under `work/orchestration/goals/<goal>/` using the `/run-goal` skill (fusion-tea). Nothing runs until it is grounded.
2. Evidence. A research task calls `scripts/source_registry.py` (fusion-tea), which runs `agentic-mbse extract` on a PDF or URL and commits a cited source under `knowledge/`; insights are recorded with `agentic-mbse pm add-insight`.
3. Model change. A modeling task runs the modeling PM commands (`/spec-model` → `/implement-model`, installed from agentic-mbse), edits the SysML text under `models/`, and validates it with `agentic-mbse validate`.
4. Compile and pin. The same task runs `sysml-codegen generate` and `snapshot`, then re-pins `studies/manifest.json` (a pin is the recorded set of fingerprints that names one exact package version; every study in a round runs against one pin); a later task runs `scripts/integrate.py` (fusion-tea), which invokes every producer again in place and returns one `CANDIDATE` or one `BLOCKER`.
5. Study. A task uses the `/run-study` skill (fusion-tea): `scripts/study/indicators.py` and `preflight.py` gate the plan, the package executes through teax's study runner and store, `verify.py` samples the store against `verify_stellaris.py` (the oracle: an independent, hand-written re-derivation of every formula), and the record is committed. A fresh session reads only the record and writes `synthesis.md`.
6. Reading and next task. The round agent reads the synthesis, proposes what each finding means, and a fresh session checks that reading before any follow-up runs. The next task is chosen from that evidence; when the round closes, another fresh session reviews it and writes the next strategy. Section 6 walks one real pass through steps 1–6.

How to navigate fusion-tea (the structural view):

- `models/library/` is concept-agnostic: `analyses/` holds the 57 calc defs and 11 constraint defs (`mfe_viability.sysml` is where limits live); `cost_structure/` the cost-account hierarchy. `models/designs/stellarator_09/stellarator_plant.sysml` is the one instance: the subsystem parts (magnet, blanket, shield, vessel, turbine and the rest), the held design values with their citations, and the `assert constraint` sites.
- `exploration/stellarator_e2e/generated/` is the compiled package: `pipelines/pipeline.yaml` (81 wired modules), `modules/` (wrappers), `handwritten/` (60 implementations), `inputs/` (205 entry-point values as JSON), `contracts/` (the fingerprints). `verify_stellaris.py` beside it is the independent oracle.
- `exploration/stellarator_e2e/studies/` holds one directory per study (nine committed, one in flight), `manifest.json` (the pin), `DISCOVERY_LOG.md` (165 finding rows), and `ANNEX.md` (package-specific facts).
- `work/` is the modeling PM (`BACKLOG.md`, `active/`, 33 items in `completed/`); `work/orchestration/goals/<goal>/` holds `goal.md`, `trail.md`, `learnings.md`, `evidence/` for each of nine goals; `work/orchestration/GOAL_RUNBOOK.md` is the one procedure.
- `.project/` is the coding PM: `adr/` (10 architecture decision records, the ADR-000N files cited below), `concepts/`, `CURRENT_WORK.md`. `knowledge/` holds 30 registered sources and `KNOWLEDGE.md` (11 recorded insights). `scripts/integrate.py`, `scripts/study/`, `scripts/source_registry.py` are the seams; `.claude/skills/run-goal` and `run-study` are the two agent entry points.

## 3. The compiled model runs one way, with no loops, by design

The owner named the limitation early: "our DAG-based compilation restrict the primitive forms we can use (closed-form algebra, acyclic). We cannot do algebraic loops or other things that would result in an irreducible block" [OWNER-VERBATIM 2026-07-25, `.project/concepts/study-driven-model-development.md`]. A DAG is a directed acyclic graph: every calculation reads only from calculations that ran before it. The compiler enforces this literally: it walks the graph of calculations and stops with an error naming every calculation in any loop (the cycle check, `_validate_producer_cycles` [code: `sysml-codegen/src/sysml_codegen/elaboration/graph.py`]), and every generated calculation runs after everything it reads from (a topological order [doc: `docs/architecture/reference/00-pipeline-overview.md` REQ-PIPE-04]). There is no solver, no iteration across modules, no time.

What you get for that: every point evaluates in about a second, the same inputs always give the same bytes, and a hand-written oracle can re-derive every formula and agree to 1e-9 [measured: `20260905-stored-energy-basis/results/verification_summary.json`, worst 4.25e-16]. What you give up: you cannot ask the model "what temperature makes the power balance close?" You can only ask "at this temperature, does it close?"

Because loops are forbidden, the team wrote rules for how physics may enter the model [AGENT, ratified 2026-08-21, `modeling_project/STUDY_POLICY.md` §§ 1–4]:

- Only inequalities are asserted over swept axes. An equality asserted over a sweep collapses the feasible region to a thin surface no grid lands on; an equality belongs inside a calculation, where it holds by construction (§ 1).
- Sweep axes are "justifiably the causal DESIGN parameter" [OWNER-VERBATIM]: geometry, field, density, technology, efficiency, finance. Never a computed quantity (§ 2).
- When physics is a genuine loop, climb a ladder (§ 4): R1 re-examine causality (one edge is usually a design choice plus a margin); R2 collapse the loop algebraically; R3 merge the cluster into one calc def whose body is a hand-written iteration, its file hash recorded so regeneration cannot silently replace it, and mirrored in the oracle; beyond that, record the cycle rather than work around it.

The sustainment chain is the live R3 case. Required heating depends on confinement time, which depends on stored energy, which depends on the helium ash, which depends on the fusion rate. `'Plasma Sustainment'` [code: `models/library/analyses/mfe_plasma_sustainment.sysml`] takes the machine and the operating levers as inputs and returns the required auxiliary heating; its body, `plasma_sustainment_impl.py`, finds the helium-ash level by guessing it, recomputing it from the guess, and repeating until it stops changing, with a cap on tries (a damped fixed-point iteration); if it never settles, the calculation errors out rather than silently accepting a bad value. Then `'Sustainment Limit'` asserts required ≤ installed, and since WI-043 `'Burn Hold'` asserts required ≥ 0 [code: `mfe_viability.sysml`]. The sign is the physics: a point whose requirement is positive is a driven plasma (it needs auxiliary heating to hold its temperature); a point whose requirement is negative is an ignited plasma (its own fusion heating exceeds every loss, so no non-negative heating closes the balance). With both limits asserted, a point passes only when its requirement lies between zero and the installed heating, so every passing point is driven. The earlier attempt to solve for the settling temperature instead found no stable root inside the limits and was abandoned as a strategy blocker [INHERITED: `work/orchestration/goals/operating-point-closure/`, round 1]. The count that shows how far the text carries the model: of 60 calculation implementations in the package, 57 are compiled from SysML expressions and 3 are hand-written (fusion power integral, replacement cost, the sustainment chain) [code: `AUTO_IMPLEMENTED` flags under `generated/handwritten/`].

[Dropdown: What is a verdict?] Each asserted limit evaluates per design point to satisfied, violated, or indeterminate (it could not be computed) [doc: `teax/docs/evaluation-and-study.md`]. A point returns a cost and ten verdicts. The ten, by their names in the pinned package [code: `work/orchestration/goals/burn-control/evidence/T-002_baseline_result.json` `verdicts`; definitions in `models/library/analyses/mfe_viability.sysml`]: net power positive (`net_positive`), recirculating-power threshold (`recirc_ok`), plasma beta limit (`beta_ok`), neutron wall-load limit (`wall_load_ok`), tritium-breeding floor (`tbr_ok`), conductor peak-field limit (`peak_field_ok`), conductor strain limit (`cond_strain_ok`), winding-pack stress limit (`wp_stress_ok`), sustainment limit (`sustainment_ok`), burn hold (`burn_hold_ok`). A cost with a violated verdict is not an answer; it is a reason to look at the constraint.

## 4. A model change becomes usable only as a proven, fingerprinted pin

The unit of change is a modeling work item through the modeling PM: spec → design → plan → implement, with validation rows (SV) and traceability rows [doc: `CLAUDE.md` Modeling PM]. WI-043 is the current instance: twelve requirements, seven design decisions with a prototype, five plan phases, and three commits, one for the model text and its design and plan (`b7e2d534`), one for the regenerated package with its re-pin and validation rows (`a7afd8f1`), one for the tests and the study battery's run of record (`e7818fdf`) [INHERITED: `work/orchestration/goals/burn-control/trail.md` T-001 return; commit subjects from `git log`].

After the text changes, the package must be regenerated and re-pinned, and this is where a text model earns its keep or loses it. Three fingerprints name a package [code: `studies/manifest.json`; `sysml-codegen/contracts/seal.py`]: the semantic fingerprint (a hash of what the model means), the executable fingerprint (a hash of the package bytes), and the indicator-input fingerprint (a hash of the inputs and wiring a study reads). Regeneration rewrites the compiled modules and preserves the hand-written ones; the snapshot is recaptured; the manifest's fingerprints are recomputed; the census of 205 entry points is re-derived; the known-answer fixtures are restated from the live package, never by hand [INHERITED: memory `gotcha_repin_after_regeneration`; trail T-001].

Then the integration seam proves the result [code: `scripts/integrate.py`; ADR-0009]. It runs ten gates in the producers' own order and requires each to change nothing (these ten are checks on the package; the ten verdicts of section 3 are checks on the physics at a design point, and the matching count is a coincidence). The ten, as the seam orders them [code: `scripts/integrate.py` `GATES`]: (1) the pinned toolchain wheels match their recorded hashes; (2) the teax checkout is at the expected revision; (3) regenerating in place moves no package byte; (4) the hand-written implementations survive regeneration byte for byte; (5) the recaptured snapshot and the re-derived entry-point census match what is tracked; (6) the model-family spine tests pass; (7) the manifest validates and its pin recomputes to the recorded value; (8) the six study preflight gates pass; (9) the oracle agrees and every verdict re-derives over an executed store; (10) the live fingerprints match the lineage the caller named. It returns exactly one `CANDIDATE` or one `BLOCKER` naming the producer that stopped it, in 15–20 seconds. "The seam proves; it does not perform": it refuses model work that has not been regenerated and committed [doc: `docs/integration_seam_operator_guide.md`]. That candidate is the pin every study in the round runs against.

Rules that keep an update honest, each decided by the owner or ratified [INHERITED: goal invariants in `burn-control/goal.md`; ADR-0004; ADR-0010]:

- Nothing is tuned. When WI-041 anchored the wall-load check to the paper's printed peak and the baseline flipped from satisfied to violated (4.088 against 4.05 MW/m²), the flip was disclosed in the model text, not adjusted away.
- A round promotes at most one pin. Comparisons are made by case id against the committed record of the earlier study, never against a re-run of it.
- Records are append-only. A correction is a dated Amendment or Addendum; a finding row in the discovery log gets a joined disposition row and is never edited.
- An audited change to a held design input is carried into the oracle under an explicit ruling; a study may never edit the oracle (ADR-0010).
- A round records the fingerprint it ran on; a run that resumes onto a changed fingerprint re-grounds first [doc: `GOAL_RUNBOOK.md` § When a cited artifact moves].

Not present, stated as a finding: there is no automatic staleness propagation across study records or goal trails. Staleness is caught by re-reading cited artifacts at resume and at review, and by the seam refusing a drifted package. The staleness design at `.project/concepts/staleness-propagation.md` is for the older concept-analysis pipeline and is marked Proposed.

## 5. A study leaves a record a stranger can audit

"A study runs a model package over a set of parameter points and records what the model's own objective and constraints did at each one. What makes it a study rather than a sweep is the record" [doc: `.claude/skills/run-study/SKILL.md`]. Three roles keep it honest: the user sets intent and rules on any axis on which no asserted limit responds; the executor works the runbook and commits the record; the administrator, a session that reads nothing outside the record directory, writes the synthesis and reports missing facts as missing.

The runbook has seventeen steps; five stages carry the mental model [doc: `.claude/skills/run-study/runbook.md`; the full 17-section record contract is `record-template.md`]:

- Declare intent and axes. The user's goal is copied verbatim. Each swept axis is a design lever declared as a complete group of package inputs, and an indicator tool reports whether any asserted limit can respond to it. An axis nothing resists needs the user's ruling, and the plan meets a fresh critic before any point runs.
- Prove the baseline and the package. The pinned baseline point is run and six preflight gates check it: the declared inputs exist, the baseline reproduces its recorded cost, the fingerprints agree, the tree is git-clean.
- Run and record. The oracle scans the candidate range and the window is fixed with its provenance stated (engineered or sourced). Points execute through teax's study runner and store; every point carries a case id.
- Verify against the oracle. A stratified sample of stored points is re-derived by the independent oracle; every verdict is re-derived too.
- Write the findings and what is missing. Each finding gets a discovery-log row; the record ends with a snapshot digest and a section saying what it does not contain. Steps 2–5 of the behavioral view in section 2 are this stage sequence seen from outside.

Only mechanical conditions stop a study (a missing key, a fingerprint mismatch, a dirty tree). A result that looks wrong never stops it; it is recorded and argued. Records must pass `tests/study/test_records.py` before commit.

The finished instance is `20260905-stored-energy-basis` [measured: its `synthesis.md`, a fresh administrator's independent recount agreeing with the record in every cell]. Four arms re-executed the previous study's 7,712 points at the pin where the helium-ash profile follows the paper's own rule. Findings: at that rule 510 of the 681 previously "driven" points ignite (their computed heating requirement goes negative); 1,839 points satisfy all nine verdicts but only 726 are driven; the cheapest driven point is 202.192 $/MWh at R 15.7 m, a 2.2 m, 13 keV (a point the earlier window never proposed); the machine as designed (R 12.7, a 1.3) at 100 MW wall-plug heating has exactly one driven point, the baseline itself, at 322.318 $/MWh with 49.08 MW required against 50 installed. Preflight 6/6; verification 20 sampled rows, 13 channels within 1e-9. That reading is what made the next goal necessary.

## 6. Each round pursues one grounded question and lets the evidence pick the next task

The owner's requirements for the layer above studies [OWNER-VERBATIM, `.project/concepts/goal-driven-model-development-harness.md`]: "user sets a goal, and the system can execute the different stages and loop autonomously"; "for any of the 'study'-looking goals, I FULLY expect the outcome 95% of the time to be 'that doesn't seem quite right, we need to revisit the model'"; "we MUST design for 'resumes'"; "I have found that criticism is pretty much required to get good results."

What `/run-goal` is: a skill file that names three roles (operator, round agent, fresh reviewer) and four modes (ground, round, checkpoint, review) and then points at one procedure, `work/orchestration/GOAL_RUNBOOK.md` [code: `.claude/skills/run-goal/SKILL.md`]. It is not a running service; a session picks it up, does one bounded piece, and writes to disk. A goal is a grounded question in `goal.md`: the question, who will use the answer, what "answered" means, what must not change, the limits, and the decisions the owner keeps. A goal hollow in any of those authorizes no task: the runbook says so, and a session asked to run it must stop and name the missing part. A round is one agent pursuing one written strategy, one task at a time, with at most one proven package version and one study, and no future task list (ADR-0001): the next task is chosen only after the previous one returns. Merge, push, item close and every reserved decision stay with the owner. The trail is append-only and is the replay record; `learnings.md` gains an entry only when a review accepts it.

The mechanics, for skimming [doc: `GOAL_RUNBOOK.md` §§ Running one task, Opening and closing a round, The two checks are distinct; ADR-0002, ADR-0005]:

| Piece | What it is |
|---|---|
| Task scope and return | Six lines written before any work (objective, why now, scope, inputs, done when, stop when); a return with one of six outcomes: `COMPLETE`, `BOUNDED_NEGATIVE`, `PREREQUISITE`, `STRATEGY_BLOCKER` (closes the round), `OWNER_GATE`, `MECHANICAL_FAILURE` (one identical retry allowed) |
| Round close | Exactly one of six triggers: a valid study reading, a strategy blocker, a changed meaning of "better", an unresolved owner gate, a declared limit, or the goal answered; then a mandatory written result |
| Two fresh checks | A lightweight checkpoint reads a study reading and its proposed follow-ups before any follow-up executes; a thorough review reads the whole round after it closes and writes the next strategy |

[Dropdown: Why "fresh" means a new session, not a different task?] "The critic is never the author's session" [OWNER]. An agent can honestly say it did not do a piece of work while still holding the whole round in context. An agent that reaches a review gate and cannot start a session stops and hands back; it never reviews itself.

The current goal, `burn-control`, is the worked example [INHERITED: `work/orchestration/goals/burn-control/goal.md`, `trail.md`]. Origin: the previous goal's review recommended it; the owner delegated the judgment ("I need to lean on you for judgement ... give me a clean proposal") and ratified the proposal the next day ("yes, please proceed with that /run-goal"). So the model's one-sided check (required ≤ installed) was passing plasmas the heating system cannot hold. The question became: make the check two-sided, 0 ≤ required ≤ installed, and see what the feasible counts become.

## Judgment

All judgments are [AGENT].

- Concerns. (1) The only external check of the model is the closed 1costingFE handshake and a hand-written oracle whose independence is arithmetic only: its inputs mirror the model's own held bindings (ADR-0010), so it cannot catch a wrong held value. The ARIES-CS comparison is the test that would; it has not run. (2) The demo branch carries known test debt: 64 fail-closed cases in `tests/study/test_study_publication_fail_closed.py` fail on this branch because six demo studies do not yet declare their columns (`CURRENT_WORK.md`, 2026-09-05 note). A reader who runs the battery will see red. (3) Ten verdicts, one concept, one instance. The oracle is demo-scoped and does not scale to the ~13 concepts the investigation names; nothing yet shows the loop at fleet scale. (4) The explainer's target reader will meet a lot of vocabulary (pin, seam, verdict, driven, ignited, fingerprint). Each is defined once above, but the render must keep those definitions within reach.
- Unresolved uncertainty. How much of the toolchain's value is the tooling and how much is the discipline in the runbooks is not separable from this evidence; a team with the same rules and plain scripts might get similar results. No productivity or velocity measurement exists; "seventeen days, four material model corrections" is a count, not a rate.
- Disagreements between sources. The teax explorer reads 1costingfe as a sibling with no wiring into teax (its own to-do notes "No TEAx module wrapper"), while fusion-tea artifacts treat 1costingFE as the reference the model was checked against and cites for cost formulas. Both are true: the handshake was done by a fusion-tea script feeding the SysML package 1costingFE's point, not by running 1costingfe inside teax. The `manifest.json` carries no constraint catalogue (0 entries) although the package has ten verdicts; the verdict set is carried by the baseline block and the route's `EXPECTED_CONSTRAINT_COUNT`, which the trail notes as a literal that must be restated by hand.
