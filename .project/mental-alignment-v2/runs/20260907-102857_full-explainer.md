# TLDR

1cFE wants to know what would have to be true for fusion electricity to cost a cent per kilowatt-hour. Answering that means searching a large design space before anyone builds anything, and the owner's framing question for this effort is: how much useful feedback can we get before building, and how can that feedback make the building count for more?

This project's answer is a machine you can ask questions of. A fusion plant is written down as text (SysML v2), compiled into a program that computes the plant's consequences in one direction (sysml-codegen generates it, teax runs it), and swept over design choices in a **study**. Every physics or engineering limit the model knows about returns a verdict at every point. Those verdicts are the feedback. When a sweep shows nothing resisting some choice, or a limit firing where the source paper says the design works, the model is telling you where it is too shallow. A **goal** is the loop in which a round agent takes such a finding and makes one bounded model change, an integration check proves the regenerated program is exactly the model, the agent re-runs the study, and an agent who did not do the work reviews the whole round before anyone builds on it.

The difference from 1costingFE, the team's own costing engine, is the direction of computation. 1costingFE decides in code what is input and what is derived, and solves fusion power backward from a net-electric target. This system computes forward from engineering choices and only asserts viability, so any lever can be swept and any limit added, at the cost of never solving for anything. The two were reconciled to one part in a million on the cost accounts, and the owner then ruled the reproduction closed so the model could grow past it.

The best evidence it works is one continuous thread on a stellarator model built from the Stellaris design paper. The model said the paper's design point needed 90.6 MW of heating against 50 installed. A goal traced the gap to how helium ash was shaped in the plasma; the sourced fix moved the requirement to 49.08 MW, on the boundary, with nothing tuned. The re-run sweep then showed most "feasible" points were ignited plasmas the model could not hold, which became the next goal and a new constraint. Nine goals and ten committed studies have run this way since late August 2026. The ARIES-CS blind comparison, the demo's biggest planned test, is still sealed.

# Why this exists: feedback before building

The owner's ambition sets the bar every capability below has to clear. In the owner's own words: "What would it take for us (humanity) to rapidly accelerate real innovation and progress in the world of physical technology?" (`.project/concepts/physical-innovation-narrative.md` § 1, `[OWNER-VERBATIM]`). Fusion carries both the promise and the difficulty. The owner is explicit that AI working in bits will not deliver a reactor; hardware still has to be built. The leverage is in choosing what to build and learning more from each build: invest in the concepts with the most promise, and understand "exactly *what* needs to be demonstrated for some larger concept to be viable" (`[OWNER-VERBATIM]`).

The recurring question was proposed by an agent and ratified by the owner on 2026-09-04: "How much useful feedback can we obtain before building, and how can that feedback make the building count for more?" The owner gave the shape a callback should take, as an example rather than fixed wording: "If we can do [X], we can achieve leverage by getting useful [feedback/data/inform]" (§ 2). Each capability below is worth having only if it produces feedback that could change a real investment or demonstration decision.

The technical motif is AI for software → AI for systems. The owner wants two threads kept together (§ 3, `[OWNER]`): transfer the patterns that made AI-assisted software development work, and name the core differences met along the way. An agent's candidate connecting idea, not yet ratified as wording: textual models, version control, automated checks, and agent workflows transfer; but executing a physical-system model reveals the consequences of its assumptions, and whether those assumptions describe reality needs engineering evidence. That is the hinge of this document. In software the test suite is the ground truth. Here the "test suite" is a model of a machine that does not exist, so every check must compare the model against something outside itself: a cited source, an independent calculation, another tool, or a sealed hold-out.

The concrete test is this project, building on the owner's published post "Searching the Fusion Design Space Systematically" (1cf.energy). That post set the frame: 1cFE is not designing a reactor; it is mapping the corridors of the design space where sub-cent economics might be reachable, which needs a search broader and faster than whiteboards and spreadsheets. It chose SysML v2 because the language is now textual (models get git, diffs, review, and coding agents) and separates a *definition* from a *usage*, described a six-level validation stack as the model-world CI, and named what it could not yet do: execute models, manage data, give users a way in. What follows is what the team built after that post, across the five areas the owner named (§ 4): research and knowledge organization, code generation, studies, the goal harness, and the stellarator work with the ARIES hold-out. Per the inherited note there, the ARIES-CS comparison is still planned, not evidence.

# The whole system is four layers, and the thread below walks up through them

Four ideas are enough to follow the thread.

1. **The model is text that describes a plant as a forward calculation.** Library files say how things are computed in general (`calc def 'Plasma Sustainment'`, `constraint def 'Burn Hold'` in `models/library/analyses/`). Two design files wire a specific plant: `models/designs/generic_mfe/mfe_plant.sysml` defines the abstract `'MFE Power Plant'` and asserts the five limits any magnetic-fusion plant must meet (net power positive, recirculating fraction, conductor peak field, winding-pack stress, conductor strain); `models/designs/stellarator_09/stellarator_plant.sysml` declares `part stellaris : 'MFE Power Plant'`, binds the Stellaris values, and adds the five limits specific to this machine (beta, wall load, tritium breeding, sustainment, burn hold). Inputs are engineering choices: major radius `R`, minor radius `a`, coil current, peak density, peak temperature, wall-plug heating. Outputs are consequences: fusion power, wall load, stored energy, cost accounts, LCOE.
2. **The executable is a generated package that computes that calculation in one direction and returns verdicts.** A *verdict* is what one asserted constraint says at one design point: `satisfied`, `violated`, or `indeterminate`. The project calls a constraint that bounds the feasible region a *fence*. Ten verdicts today. Nothing is ever solved for; the package cannot answer "what temperature makes this work," only "does this temperature work."
3. **A study is a question an executor puts to the package by sweeping causal levers and reading the verdicts.** Its product is a *record*: one directory a stranger can read to recover what was asked, what was assumed, what came out, and what none of it supports. Every study runs against a *pin*, the exact package version, named by a digest, so two results are comparable.
4. **A goal is the loop in which agents grow the model from what studies find.** A grounded question pursued in rounds; in each round an agent makes at most one model change and runs one committed study; an agent who did not do the work reviews each round; the owner holds the gates that matter.

The physics is deliberately modest: one part-tree level deep with 14 leaf subsystems, not a plasma simulation. What makes it interesting is honesty: every number cites a source or is computed from one, every verdict is data, and every change is measured against the previous state.

**Visual:** a four-layer stack (model text → sealed package → study record → goal trail) with two arrows: verdicts flowing up as feedback, one bounded model change flowing down per round.

# Step 1: the modelers gave the model a confinement calculation, and it said the paper's design point needs 90.6 MW against 50

The story starts where the model's output first contradicted its own source, because that contradiction is what every later layer exists to handle. The stellarator model is bootstrapped from the Stellaris design paper (concept 09, a quasi-isodynamic HTS stellarator, R = 12.7 m, a = 1.3 m), which says its design point runs with about 50 MW of plasma-coupled heating installed.

Until late August the model had no confinement physics. Magnetic field reached no plasma quantity, so a sweep found LCOE rising with field everywhere and the cheapest point at the lowest field the beta limit allowed. The study's executor logged that as a finding: the model had no confinement closure (`DISCOVERY_LOG.md` row `20260823-magnet-technology-ab#4`). Goal `operating-point-closure` took it up, and its round agent built WI-037: from the paper's own appendix equations (the ISS04 confinement scaling in closed form, radiation, alpha heating), the model now computes how much sustained heating a chosen density and temperature need, and asserts `sustainment_ok`: required ≤ installed. At the paper's design point the model said **90.6 MW required against 50 installed**. Violated. The modelers recorded it as an honest residual and tuned nothing. The headline LCOE at that pin was 307.087 $/MWh.

To see why that number could be trusted enough to argue with, you need to know what the executable is and what it cannot do.

# The executable computes in one direction only, which is both the point and the limitation

The 90.6 MW was worth arguing with only because the program that produced it is provably the model text and nothing else, so here is what that program is. sysml-codegen turns the model text into a directed acyclic graph (DAG): modules with typed inputs and outputs, ordered so that no module reads from one that runs later. teax runs that graph. Every value the package takes from outside is an *entry point* with a qualified key such as `stellarator_09__stellaris__R`; the stellarator package has 205 of them (the census). Every value it produces is a *channel* such as `stellarator_09__stellaris__lcoe_calc__lcoe`. Constraints evaluate to evidence, never exceptions, under three-valued logic. The package is *sealed*: its `contracts/` directory (contracts, a generation manifest, its own `verify.py`) lets a runner check it is the package the model produced. When a calculation cannot be expressed in the generator's arithmetic (the sustainment chain integrates profiles numerically and iterates on the helium-ash peak), the generator marks it `manual_required`, emits a stencil, and a modeler writes the body under `handwritten/`; on regeneration the generator preserves those bodies when their signature still matches (`--smart-regen --preserve-handwritten`).

What that buys: determinism, a complete provenance chain, and the ability to add a lever or a limit without deciding in advance what is "input." What it costs: no feedback loops and no solver (a cycle across modules is refused at generation; a cycle inside one calc def goes to a handwritten rung); units are metadata only; `sum()` is the only recognised aggregation.

Real physics has loops, so the team wrote down how to meet them before it did. `modeling_project/STUDY_POLICY.md` § 4, ratified by the owner on 2026-08-21, is a four-rung ladder applied top-down because each rung is cheaper than the next: **R1** re-examine causality (many "cycles" are a lever plus a margin: on-axis field is what the designer chooses, so "can the conductor deliver it" enters as an inequality); **R2** collapse the loop on paper into a closed form; **R3** merge the coupled cluster into one calc def that returns the consistent tuple, the iteration living in a handwritten rung mirrored by an independent *oracle* (a hand-written Python copy of the model's equations, kept bit-identical to the package at every pin, so the package can be checked against something that is not itself); **R4** seed one variable from a coarse lever-derived estimate and assert a validity band. A cycle that resists all four goes into a tripwire table (§ 8, still empty) rather than being worked around. The sustainment chain is an R3 case in production: a damped fixed point on the ash peak (tolerance 1e12 m⁻³, cap 200 iterations, fail loudly, never clamp), mirrored by the oracle.

The policy also names the failure the owner feared (§ 1, 2026-08-02): as findings become constraints, the feasible region could collapse to a thin manifold. Inequalities cut the space but leave it full-dimensional; an *equality* asserted over swept inputs drops a dimension, a grid never lands on it, and the verdict column reads ~100 % violated and carries no information. Hence the axis rule, in the owner's own words: "it should be justifiably the causal DESIGN parameter. E.g. choose all geometry and input powers, and get an output power" (§ 2, `[OWNER-VERBATIM]`). Sweep only levers; internalize equalities as calcs; when a refinement computes a quantity that used to be a lever, retire the axis.

(Dropdown candidate: the guard pattern. After internalizing an equality, a thin assert compares two quantities the calc already computed, so the physics lives once and the assert doubles as a detector of unfaithful generated code.)

# 1costingFE solves backward for a fixed set of inputs; this model computes forward and asserts

The one-direction property is exactly what separates this from the tool 1cFE already had, so the contrast belongs here. 1costingFE (`~/1cfe/1costingfe`) is the team's costing engine: hand-written Python, 17 confinement concepts, the CAS10–CAS90 cost accounts, one `forward()` that solves fusion power *backward* from a net-electric target, with evaluation order fixed in code and YAML that holds numbers but never equations (as reported by an explorer agent from `src/costingfe/model.py`). To change what is derived you edit Python.

The owner's framing: "Whereas most custom TEA tools like 1costingFE need to decide 'what are the inputs' and 'what gets derived' (which can then be painful to change later), this is totally generalized to forward-pass and assess only. Not necessarily 'better', just has its own pros and cons" (`[OWNER-VERBATIM]`, `stellarator-mbse-demo.md`). The trade is concrete: to compare the two, the modelers had to *feed* the SysML model the plant point 1costingFE had solved for, exactly the capability forward-pass gives up.

That comparison (Anchor A) is closed evidence. Fed 1costingFE's own inputs, the generated package reproduces 27 of 32 cost rows within 1e-6 relative, and the other five miss only through one itemized remainder, a $0.72 M vacuum-pumping sub-account the model does not carry; the end-to-end LCOE gap reconciles to the itemized sum within 5e-08 in both financing conventions (`exploration/stellarator_e2e/HANDSHAKE_REPORT.md`). Then the owner ruled on 2026-08-30: "I'm done caring about the 1costingFE reproduction. we showed we could do it. pin it, or archive those models. but let's move on -- I do not want to be anchored to 1costingFE." The mechanism was *pin*: the state where the handshake holds is recorded at commit `f22bd288` and no later goal re-runs it (`work/orchestration/stale-basis-recompute.md` § Addendum). 1costingFE stays the validation reference wherever a direct comparison is possible and is never a limit on what the model may contain (`STUDY_POLICY.md` § 10, `[OWNER]`); each held number the modelers turn into a computed one is, in the policy's words, the demo's differentiation evidence.

# Step 2: a round agent traced the 90.6 MW to the helium-ash profile, and the sourced fix moved it to 49.08 MW

With the executable trusted, the 90.6 MW became a question worth a goal. The round agent for goal `stored-energy-basis` (grounded 2026-09-05, closed 2026-09-06) noticed the model's plasma stored energy W was 551.4 MJ where the paper prints 504.65, a +9.2 % gap, and conducted loss rises steeply with W. Scaling W to the printed value inside a copy of the oracle flipped both failing verdicts (`sustainment_ok` and `wall_load_ok`), but the same arithmetic showed no reading of the paper's own profiles reaches 504.65 MJ, so the agent proposed and the fresh reviewer accepted that the printed number is *not a target* (learning L-002). Round 1 attributed the gap: most of it came from giving the helium ash the fuel's flat profile where the paper's rule peaks it in the core; the rest from profile exponents and from the paper's own inconsistency. The owner ruled on 2026-09-05: "we should fix the ash profile (and make sure this scales up for larger stellarators). and I don't want to add the footnote."

WI-042 landed in round 2: the ash follows the fusion-rate shape at every point (Stellaris Eq. A.5 applied pointwise), electrons by quasi-neutrality, one pressure integral for W and beta. At the design point W fell to 519.9 MJ and the required heating to **49.08 MW against 50**, satisfied by 0.92 MW; the wall-load peak came under its limit too. LCOE moved 313.513 → 322.318 $/MWh. Nothing else changed. (The full before/after table is in the appendix.)

Two ideas made that round possible: the goal discipline that let an agent pursue a question without drifting, and the update discipline that made WI-042 a pinned package rather than an edited file.

# A goal is a grounded question pursued in bounded rounds, with a fresh critic between rounds

The ash round could only be trusted because the agent running it was held to a shape that made drift visible, and that shape is the goal layer. A goal is "a grounded question someone wants answered, pursued in rounds" (`work/orchestration/GOAL_RUNBOOK.md`). The layer "decides *what to work on next and what the evidence means*. It does not do the work"; the work happens in the native workflows, and the goal layer **cites and never restates**. The owner's reason for building it: "user sets a goal, and the system can execute the different stages and loop autonomously," operated by someone who "shouldn't have to be me" (`goal-driven-model-development-harness.md`, `[OWNER-VERBATIM]`). The owner also predicted the usual outcome: "for any of the 'study'-looking goals, I FULLY expect the outcome 95% of the time to be 'that doesn't seem quite right, we need to revisit the model'."

`/run-goal` is the skill an operator or agent invokes to work this layer (`.claude/skills/run-goal/SKILL.md`; the procedure itself lives in `GOAL_RUNBOOK.md`). It has four modes, chosen by the state of the goal directory: `ground` writes `goal.md` with the operator when none exists or it is still draft; `round` opens a round with a strategy revision, or runs the next task of an open one; `checkpoint` has a fresh session review a study reading's proposed dispositions before any follow-up executes; `review` has a fresh session read a closed round and pass or fail it. The owner's "yes, please proceed with that /run-goal" on 2026-09-07 was the ratification that let the burn-control session move from `ground` to `round`.

What a round looks like, using burn-control round 1 (`work/orchestration/goals/burn-control/trail.md`). Before any task, the round agent wrote a strategy: the approach (land the second inequality, then measure), the assumptions it rests on, the conditions under which the agent would abandon it, and no task list, because a strategy that can predict its tasks is a plan, not an experiment (ADR-0001). Then one task at a time, each scoped in six lines before work began (objective, why now, what is authorized and excluded, inputs, done when, stop when), started with a one-line entry so an interruption leaves a trace, and returned with a named outcome. T-001 (the model item) and T-002 (the pin) returned `COMPLETE`; the other outcomes are `BOUNDED_NEGATIVE`, `PREREQUISITE`, `STRATEGY_BLOCKER`, `OWNER_GATE`, and `MECHANICAL_FAILURE`, and each says what happens next. A round is allowed one promoted pin and one committed study, so it stays finite and its results comparable, and it closes when a valid study reading exists, even an adverse one: "an honest empty round is a result."

Two moments belong to an agent who did not do the work. Before any follow-up executes on a study reading, a fresh reader checks the reading and its proposed dispositions (`### Checkpoint C-00N.rK`, resubmitted up to a cap; hitting the cap stops the round rather than releasing it). After the round closes, a fresh reviewer reads it end to end, returns `PASS`, `FINDINGS`, or `OWNER_GATE`, and then either recommends the owner-held close or writes the next strategy (ADR-0002, ADR-0005). The one definition of "fresh" is the owner's: "The critic is never the author's session." An agent that cannot start a fresh session writes a handoff stop and waits. The owner's reason: "I have found that criticism is pretty much required to get good results" (`[OWNER-VERBATIM]`). Merge, push, item close, and every reserved gate stay the owner's.

Three files carry all of it: `goal.md` (the question, what "answered" means, the invariants a comparison must preserve, the limits, the gates the owner keeps, and the grounding evidence; the operator refuses to open a round on a goal hollow in any of those, a rule the owner widened after a probe caught cold sessions running tasks on under-specified goals), `trail.md` (append-only: what happened and what was decided), and `learnings.md` (what the run now knows, accepted by the fresh review). `.project/adr/` holds the reasons. That leanness is itself a ruling (ADR-0003): prose files and git first, control-plane machinery only when a real run shows prose failing. The two proof runs recorded ten and eight prose failures and promoted nothing; a cold session, the fresh reviewer, or the operator caught every one.

# A model change is a work item that ends in a re-pinned package, never a tuned number

The other half of the ash round is how WI-042 became a package a study could run against. It was not a file edit. A model change is a modeling work item (`work/active/WI-NNN_slug/` with `spec.md`, `design.md`, `plan.md`) carried through `/spec-model → /design-model → /plan-model → /implement-model`, with agentic-mbse's six validation levels (syntax, structure, dataflow, constraint coverage, traceability, architecture) at the phase boundaries and every quantitative value carrying a `Source`/`Ref`/`Basis` citation (requirement MR-4). `work/BACKLOG.md`'s frontmatter is mutated only through `agentic-mbse pm` verbs.

Implementation ends with regeneration: edit `models/` and the staged twin under `exploration/stellarator_e2e/models/`, regenerate, recapture the snapshot, re-derive the 205-entry census, restate the test fixtures, and re-pin `exploration/stellarator_e2e/studies/manifest.json`. That manifest freezes what the package is expected to say: the baseline point (R 12.7, a 1.3, availability 0.85), the headline channel's value (322.31843948570247 after WI-042), and the expected verdict for each constraint. When a change is *expected* to move a verdict, the item says so before it lands. WI-041's wall fence was designed to read violated at the baseline (4.088 against 4.05), "disclosed, never tuned," and the modelers updated the manifest's expectation as a deliberate committed step.

The invariant written into every goal is that **nothing is tuned**. The requirement, W, the ash rule, the transport facts, the coupling, and the installed heating are "never moved to open or close a region" (`burn-control/goal.md` § Invariants). A calibration reproduces the paper's *inputs*; the model's *outputs* are left free to disagree. The consequence is on record in the goal-overview narrative: across the maturation goals the reference design's LCOE rose from 275 to 313.5 $/MWh (322.3 after WI-042) and it began failing checks it had passed. "That is the model getting more honest, not drifting."

# Step 3: the executor re-ran the committed window and found 510 of 681 "feasible" points were ignited plasmas the model could not hold

A single point being satisfied says little; the round agent still had to show what the fix did across the whole window. The executor of `20260905-stored-energy-basis` re-executed the previous study's four arms (arms are variants of the same question, run to be compared), 7,712 points, joined point by point to the committed record. Sustainment flipped 964 points from violated to satisfied and none back. The cheapest driven point moved to 202.192 $/MWh at R 15.7 m, a 2.2 m, on a temperature row the earlier window had cut off; the fresh critic had made the executor restore that row before any point ran. The fresh reviewer recommended grounding "burn control" as a goal; the owner ruled "close it" and carried WI-043 and WI-044 into the backlog.

That reading is only as good as the record it came from, which is what the study discipline exists to guarantee.

# A study is a question with a record that a stranger can audit, not a sweep with a plot

The 510-of-681 count is believable because a second agent with no memory of the run could recount it from one directory, and that is what a study is built to allow. The run-study skill defines it in one sentence: "A study runs a model package over a set of parameter points and records what the model's own objective and constraints did at each one. What makes it a study rather than a sweep is the record" (`.claude/skills/run-study/SKILL.md`).

**The record** is one directory, `exploration/<pkg>/studies/<YYYYMMDD>-<goal-slug>/`: `record.md` (seventeen numbered sections from a template), `snapshot.json` (every fingerprint and digest resolved at commit time, so deleting the manifest later cannot change what the record says), `indicators.json`, `axes.json`, `study.py`, and `results/` (`points.csv`, `excluded_points.csv`, `baseline_result.json`, `preflight_results.json`, `verification_summary.json`, `window_edges.json`). Once committed the evidence is immutable; corrections are addenda.

**The fifteen obligations of execute mode** (`runbook.md`) are easiest to hold as five moves:

1. *Capture and declare.* The owner's intent verbatim. Each axis declared at the SysML-attribute level and expanded to its complete entry-key group, because one attribute can fan out to several keys and sweeping a subset manufactures an inconsistent machine; ties no suffix scan could find are declared in the manifest (`magnet__R0` rides with `R`: the coil major radius *is* the plasma major radius).
2. *Ask what pushes back, before anything runs.* `scripts/study/indicators.py` traces, conservatively, which constraints and objectives each axis can reach through the module graph. `no_constraint_response` is a sound negative: nothing in the model resists this lever, and the owner reads that as "a signal the model is underdeveloped" (`STUDY_POLICY.md` § 9, `[OWNER-VERBATIM]`). The user rules before execution; the record carries a model-development finding either way. The executor frames each axis as `search` (expects verdict structure) or `sensitivity` (expects a monotone response) and submits the plan to a fresh-session pre-execution critique.
3. *Prove the package is the one you think it is.* Run the manifest's pinned baseline point, the six preflight gates (`scripts/study/preflight.py`), and an oracle scan that fixes the window and discloses whether its edges are `engineered` or `sourced`. A restated window is re-scanned at the new package, a rule the owner added on 2026-09-06 after the critic caught an old window's floor having been set by a fence the model change had just relieved.
4. *Run every point through the stock teax lifecycle.* No hand-rolled loop; the route is either the `teax-study` CLI over a plain grid or a study-local definition built on `StudyRunner` and `PreparedListStrategy` (`runbook.md` step 8); each point carries inputs, channels, and per-constraint verdicts into the store by qualified identity. Then `scripts/study/verify.py` checks a sample stratified by verdict combination against the oracle, re-deriving verdicts from the oracle's operands rather than comparing the package to itself.
5. *Judge, register, freeze.* Re-judge each axis's framing against the run; write every finding into § 15 with id, kind, disposition, and home (`unrouted` is a stated state, never a blank); append one row per finding to `DISCOVERY_LOG.md` under `<study-id>#<n>`; resolve the snapshot; commit.

**Administer mode** is the other half. A fresh session reads the record directory and nothing else, recounts independently, and writes `synthesis.md` with four labels kept apart: `[RECORDED]`, `[RECOUNT]`, `[MISSING]`, `[READING]`. The stored-energy-basis administrator agreed with every headline count, listed seven small disagreements, and named thirteen things the record does not support. A fact the administrator cannot recover is a defect in the record contract, not in the read.

Two choices do most of the work: *only mechanical conditions fail closed* (a missing key, a fingerprint mismatch, an unparseable artifact, a dirty package; "indicators inform; they never gate"), and *every interpretive judgment is written beside the evidence it rests on* with its provenance grade. That is why a record can be the seam between three sessions that never share context.

# The integration seam proves a package is a fixed point of its own producers, and the pin names it

`scripts/integrate.py` is the program that checks "nothing moved" instead of taking the agent's word for it. It answers one question: is there exactly one verified, study-ready candidate for this package, and if not, what stopped it? Ten gates in the producers' own order; `CANDIDATE` (exit 0) or `BLOCKER` (exit 1, one of fourteen named conditions). The decision behind it is ADR-0009: *integration is a fixed-point proof, not a transformation.* The seam regenerates the package into itself and demands zero moved bytes outside `handwritten/`; recaptures the snapshot and demands the tracked file back; re-derives the census; runs the spine tests; recomputes the manifest's pin; executes the pinned baseline; runs the six preflight gates; verifies oracle parity and re-derives every verdict; and compares the live fingerprints against the pair the caller named. So it refuses model work not yet regenerated and committed, and re-running it will not help; the goal layer reads that as `PREREQUISITE`. A run takes about 15–20 seconds. For WI-043 it returned `CANDIDATE` on all ten gates first run.

Identity is three fingerprints plus a tool revision. The manifest records an *indicator-input* digest over nine files (the model contract, seven input JSONs, `pipeline.yaml`), a *semantic* fingerprint from codegen's `model_contract.json`, and an *executable* fingerprint from the sealed package; a study also records the teax git revision. The indicator-input digest is the pin: `1d4a06b0e0e9…` for the WI-043 package. teax refuses to reopen a study store if any element of its compatibility tuple changed, so a model refinement forces a new study lineage and prior rounds stand as history. The oracle lives at `exploration/stellarator_e2e/verify_stellaris.py`, wrapped by `studies/oracle_entry.py`; ADR-0010 scopes it to the demo.

# The hard part was trust without a machine to test against, and the evidence of delivery is measurable

The arithmetic was never the hard part. It was making a loop that agents can run *and* a stranger can trust, when the ground truth is a machine nobody has built. Four things had to be true at once.

**The executable has to be exactly the model, every time.** The seam's zero-byte regeneration gate, the byte-identical snapshot, the oracle held bit-exact at every pin, and a provenance test that pins the three toolchain wheels by SHA-256 make "the model says" a claim about the text, not about a build.

**Every number has to be traceable.** Requirement MR-4 makes every value carry a citation; the modelers write `Source`/`Ref`/`Basis` blocks that cite page images, because the extracted Stellaris tables are corrupted in every row the research checked; and the research seam refuses to register a source nobody has explained.

**Interpretation has to be separable from measurement.** The record template splits values from arguments, the administrator labels every statement `[RECORDED]`, `[RECOUNT]`, `[MISSING]`, or `[READING]`, and every decision-carrying line carries a provenance grade (`[OWNER-VERBATIM]`, `[OWNER]`, `[AGENT]`, `[INHERITED]`).

**Criticism has to come from outside the author's context.** The fresh-session rule and the two checks did real work on record: a checkpoint reader caught a false R-independence claim before it reached a new goal (priced-levers); a pre-execution critic had the executor restore the 13 keV rows that held the cheapest driven region (stored-energy-basis); a critic narrowed a grounding fact and routed the model text repeating it (burn-control).

Where the demo stands, measured: criteria 1–3 are met (end-to-end run; viability constraints executing, five then, ten now; the handshake at 1e-6); criterion 5 (studies through the teax study layer) has evidence in ten committed records but is not formally closed; criteria 4, 6, 7, 8 (the ARIES-CS hold-out, visualization, the public write-up, optimum rediscovery) are not started (`epic_stellarator_mbse_demo.md`; CURRENT_WORK through 2026-09-06). The maturation phase exists because the owner was "not convinced the model quality is high enough to actually compare to ARIES"; a depth rubric written blind is the yardstick, and re-grades show magnet rows moving from 1 and 2 to 3 and 3, plasma from 2 to 3, heating from 1 to 2. The seal on `knowledge/holdout/` has held; the reveal stays owner-held.

Return to the owner's callback template. If we can compute what a chosen operating point *costs the heating system to hold*, we learn whether a published design point is one the plant as specified can sustain, before anyone sizes a gyrotron. If we can re-run a committed window at a new pin and count flips by case id, we learn which conclusions survived a physics correction and which were artifacts of the old fence. If we can register a source only with its validation recipe attached, we learn which numbers are load-bearing and which are inherited defaults, which is what the p_pump correction (1.0 → 195 MW, LCOE +21 %) exposed. None of that builds a stellarator. All of it changes which stellarator you would build, and what you would need to demonstrate first.

# Appendix

## Glossary of exact names

- **Entry key / entry point:** a package input, qualified like `stellarator_09__stellaris__R`. 205 in the current census.
- **Channel:** a package output, qualified like `stellarator_09__stellaris__sustain__p_aux_required`. The manifest's `objective_catalog` names eleven of interest, `lcoe` first.
- **Verdict:** the status of one `assert constraint` at one point: `satisfied | violated | indeterminate`. Ten today: `net_positive`, `recirc_ok`, `peak_field_ok`, `wp_stress_ok`, `cond_strain_ok` (asserted in `generic_mfe/mfe_plant.sysml` lines 1020–1047) and `beta_ok`, `wall_load_ok`, `tbr_ok`, `sustainment_ok`, `burn_hold_ok` (asserted in `stellarator_09/stellarator_plant.sysml` lines 1245–1300).
- **Fence:** the repo's word for a constraint that bounds the feasible region.
- **Driven / ignited:** driven = every fence satisfied and `p_aux_required ≥ 0`; ignited = `p_aux_required < 0`. Every count in a record says which sense it uses.
- **Pin:** the manifest's `fingerprints.indicator_inputs.digest`; the exact package version a study runs against. At most one promoted per goal round.
- **Tie:** a declared identity between two entry keys that are the same physical quantity (`magnet__R0` rides with `R`).
- **Indicators:** `indicators.py`'s conservative reachability report per axis group; `no_constraint_response` is a sound negative; `constraints_reachable` is only a possible path.
- **Oracle:** `verify_stellaris.py`, an independent pure-Python mirror of the model's equations, bit-exact at every pin; demo-scoped (ADR-0010).
- **Seam:** a documented boundary a goal round invokes: `research`, `model`, `integrate`, `study.execute`, `study.read`.
- **Fresh:** a session that did not do the work being reviewed; "the critic is never the author's session."
- **Trail headings:** `## Round N — slug`, `### Strategy revision`, `### T-00N scope | start | return`, `### Checkpoint C-00N.rK`, `### Round N result`, `### Round N review`, `### Stop`, `### Amendment`.

## Goal-layer enumerations (from `GOAL_RUNBOOK.md`)

- **Five surfaces:** `goal.md`, `trail.md`, `learnings.md`, `GOAL_RUNBOOK.md`, `.project/adr/`.
- **Five field classes a grounded goal needs:** question and answered-when, invariants, limits, reserved gates, grounding evidence.
- **Six round-closing triggers:** a valid study reading; a strategy blocker; a changed comparison meaning; an unresolved owner gate; a declared limit; the goal answered.
- **Six task outcomes:** `COMPLETE`, `BOUNDED_NEGATIVE`, `PREREQUISITE`, `STRATEGY_BLOCKER` (closes the round), `OWNER_GATE`, `MECHANICAL_FAILURE` (retry only when task, inputs, scope, and meaning are identical).
- **Five decision fields on every return:** trigger; decision and reason; tier (`execution detail | reserved gate | premise surprise`); who decided; what changed.
- **Limits (defaults, restated in every goal):** 2 retries, 2 checkpoint revisions, 6 rounds.
- **Five seams a round invokes:** `research`, `model`, `integrate`, `study.execute`, `study.read`.
