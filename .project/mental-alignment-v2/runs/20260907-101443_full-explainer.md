# TLDR

1cFE asks what would have to be true for fusion to cost a cent per kilowatt-hour. This project asks a question underneath that one: **how much useful feedback can you get about a physical machine before you build it, and can AI agents produce that feedback at scale without quietly fooling you?** Fusion is the test because it is the hardest case.

The central idea is a **forward calculation that pushes back**. An engineer writes a power plant down as text (a SysML v2 model): a few dozen chosen values, every other value computed from them, and ten limits asserted against the results. A compiler (`sysml-codegen`) turns that text into a sealed Python program. A runner (`teax`) evaluates it at thousands of design points and stores, for each point, every computed value and a three-valued verdict per limit: `satisfied`, `violated`, or `indeterminate`. That is the whole physics-and-cost engine, and it never solves for anything. It computes forward and then judges.

Everything else exists to keep that engine honest while agents change it. A **study** is one sweep plus a record a stranger can audit. A **goal** (operated with `run-goal`) is one question pursued in bounded rounds, each reviewed by an agent that did not do the work. Between a model edit and a study sits a checking program (`scripts/integrate.py`) that proves, by content digest, that the package on disk is exactly what the model says. Committed records are never edited; corrections are appended, and a stale result is re-run and joined point by point.

The proof that this works is the last three weeks on the stellarator model. A typed-in pumping power turned out 150 times too low and nothing in the arithmetic objected. The paper's own operating point read as needing 90.6 MW of heating against 50 installed; a sourced fix to one profile shape moved that to 49.08 MW with nothing tuned, and the same fix revealed that most "feasible" designs in the search window were actually igniting past the model's ability to hold them. That became a tenth asserted limit, `burn_hold_ok`, landed on 2026-09-07 with zero bytes changed anywhere else and ten integration gates passing on the first run. The study that measures it is staged and has not yet run.

What is different from 1costingFE, the team's costing engine: 1costingFE solves for the plant that delivers a requested power. This model takes the plant as chosen and reports whether it works. The two were reconciled once to the cent, and then the owner released the model from matching.

# 1. Why this exists: feedback before building, and building that counts for more

The owner's framing question, in his words: *"What would it take for us (humanity) to rapidly accelerate real innovation and progress in the world of physical technology?"* Fusion carries both halves of that question, the promise and the difficulty. Hardware still has to be built, and AI working in bits will not deliver a working reactor by itself. The leverage the owner identifies is in **where we invest and what we learn from each investment**: put money on the concepts with the most promise, and know *"exactly what needs to be demonstrated for some larger concept to be viable."* (`.project/concepts/physical-innovation-narrative.md` § 1; the quotes are the owner's.)

The recurring question the whole narrative hangs on was proposed by an agent and ratified by the owner on 2026-09-04: **how much useful feedback can we obtain before building, and how can that feedback make the building count for more?** The owner wants each capability tied back to that question in a callback of the shape *"if we can do X, we get leverage by getting useful feedback about Y."* He gave that as an example of the shape, not fixed wording.

The technical motif is a transfer. AI-assisted software development works because code is text, lives in version control, and is checked by automated tests, so an agent gets fast, cheap feedback on whether it broke something. The published post, "Searching the Fusion Design Space Systematically" (1cf.energy, March 2026), makes exactly this argument for systems models: SysML v2 has a textual form, so models can be diffed, branched, reviewed, and edited by coding agents, and a six-level validation stack plays the role of the test suite. The post is also explicit about scope: *"We are not attempting to automate reactor design."* The aim is cost floors at corridor-mapping fidelity, the assumptions that matter most, and focused development priorities.

The difference from software, as the narrative captures it (an agent's candidate idea, not yet owner-graded): **executing a physical-system model reveals the consequences of its assumptions; whether those assumptions describe reality requires engineering evidence.** A test suite tells you your code does what you said. Nothing in a model run tells you the world does what the model said. So the platform has to make two things visible at once: what the model computes, and where each number came from.

**Where this sits in 1cFE.** The project's own scope document sets a cross-concept techno-economic comparison of about 36 fusion concepts (38 research dossiers exist under `knowledge/concept_research/`) along seven axes, with one non-negotiable: every number traces to a source and every assumption is labelled, because LLM agents do much of the work and hallucinate (`modeling_project/OVERVIEW.md`). The published costing engine, 1costingFE, is the team's other track (§ 4). This track is the systems-model track, and its first big demonstration is one concept modeled deep: the quasi-isodynamic stellarator (concept 09, the Proxima Fusion "Stellaris" design paper), built without reading the ARIES-CS study, which is sealed under `knowledge/holdout/` as a hold-out for a comparison that has not yet happened. The owner set the balance himself: *"80% methodology demo... The other 20% is proof-by-example."* (`.project/concepts/stellarator-mbse-demo.md` § Owner's Words.)

**Why it is not trivial.** Three facts from the record.

- A model that only computes forward will print a smooth, plausible cost map that is silently wrong. The study concept says it in one line: at scale, *"the observed failure mode of the naive path is no observed failure, just a wrong map"* (`.project/concepts/study-driven-model-development.md` § Problem Statement). So the model has to be built to object.
- Agents drift. The loop of study, model change, research, regenerate, re-study had run exactly once, by hand, with the owner carrying "I need X" between stages in a different shape each time (`goal-driven-model-development-harness.md` § Problem Statement). Nothing said "here is the goal, the state, the next thing to do" in a form a fresh session could pick up.
- Wrong numbers were real. The primary-coolant pumping power sat at 1.0 MW, a default inherited from 1costingFE, until 2026-08-28. The sourced value is 130 to 195 MW (§ 3).

**Visual cue:** two columns, "AI for software" and "AI for systems", with the same four rows (text, version control, automated checks, agents) and a fifth row only on the right: "a run reveals the assumptions' consequences; only evidence says whether the assumptions are true."

# 2. The model in one picture: a calculation that runs forward, then judges itself

Hold this picture; every later section is one part of it.

**The description.** A plant is written as a tree of parts with attributes, in SysML v2 text under `models/`. Some attributes are **levers**, values an engineer chooses: major radius `R` (12.7 m), minor radius `a` (1.3 m), peak density `n_e0`, peak ion temperature `T_i0` (14.63 keV), coil current `I_coil`, installed heating. Every other attribute is computed by a **calc**: field from coil current, confinement time from field and density, required heating from the losses, wall load from fusion power and geometry, each cost account from sizes and prices, LCOE from the accounts. Every held number carries a `Source` / `Ref` / `Basis` doc comment naming the page or image it came from; the temperature lever, for instance, cites the paper's Table 5 image and notes that the extracted text "24.60" is an extraction artifact (`models/designs/stellarator_09/stellarator_plant.sysml:575`).

**The verdicts.** Ten limits are written as `constraint def`s in `models/library/analyses/mfe_viability.sysml` and asserted in the plant instance. Their names in the generated package: `beta_ok`, `burn_hold_ok`, `cond_strain_ok`, `net_positive`, `peak_field_ok`, `recirc_ok`, `sustainment_ok`, `tbr_ok`, `wall_load_ok`, `wp_stress_ok`. Each is an inequality between a computed quantity and a limit, and each yields one verdict per design point, three-valued (`kleene-three-valued` is the evaluation semantics recorded in the contract): `satisfied`, `violated`, or `indeterminate`.

**The program.** `sysml-codegen` compiles the description into a Python package in which every lever is an **entry point** (a qualified key such as `stellarator_09__stellaris__T_i0`; 205 in this package) and every computed value is a **channel** (`stellarator_09__stellaris__lcoe_calc__lcoe` is the headline; 113 channels). `teax` evaluates the package at a point and returns the channels and the ten verdicts.

**The two layers above.** A **study** runs the program over a set of points and commits a record. A **goal** decides which study to run next and what to change in the model, in rounds, with a fresh agent reviewing each round.

**The rule that ties it together.** Nothing is tuned to make a verdict flip, nothing committed is edited, and every artifact a decision rests on is cited by content digest. The owner's phrase for the direction of travel is that the model **"pushes back"**: each time a typed-in number becomes a calculation, the calculation reproduces the paper's inputs and the outputs are left free to disagree with the paper.

Three words the project uses that this document will lean on: a **fence** is what the study records call an inequality limit that "catches" the edge of a swept window; a **pin** is the exact package version a study runs against, named by a digest; **fresh** is the owner's word for a reviewing session that did not do the work.

**Visual cue:** five boxes left to right (SysML text, sealed package, teax run, study record, goal round) with a return arrow from the goal back to the text, and one caption under the whole row: "cited by digest, corrected by appending, never tuned."

# 3. One story shows the whole chain: a printed number, a fixed profile, and a tenth verdict

This is the strongest thread in the record and it touches every mechanism the later sections explain. It runs from 2026-08-21 to 2026-09-07. Where a number is a measurement from a committed run, it is labelled as one.

**A wrong input, and no objection (August 21 to 29).** The first study on the package, an A/B of power-cycle options, sighted a finding: the pumping power for the primary coolant, held at 1.0 MW, was about a hundred times below helium-circulator figures. The number came from a 1costingFE default and its citation was a provenance chain, not a derivation. Nothing in the model could object, because a held input has no fence. A goal named `p-pump-basis` read three EU DEMO sources and found helium-primary circulators draw 4 to 6 % of thermal power, 130 to 195 MW at this plant. The owner ruled 1.0 MW indefensible and set 195 MW, still as a held input. The next goal, `p-pump-fence`, regenerated the package and re-ran the geometry sweep: measured, LCOE rose 21 % at the reference point and the infeasible region grew from a small-machine corner into a band across the window. Getting a pin took five runs of the integration seam, which refused four times, each on a different hand-maintained copy of the old package's outputs, before certifying a candidate (`work/narratives/20260904-223513Z-p-pump-fence.md`). That is the naive path's failure in one episode: a smooth map, wrong by two orders of magnitude in one input, and only a researcher with a source could say so.

**A printed number that was not a target (September 4 to 6).** By September the model had grown a confinement chain (`'Plasma Sustainment'`, `mfe_plasma_sustainment.sysml`) that computes the heating a plasma needs to hold the chosen density and temperature, and a fence, `sustainment_ok`, that requires that heating to be no more than the 50 MW the paper installs. The model integrated its assumed profiles to a stored thermal energy of 551.4 MJ where the paper prints 504.65, a 9.2 % gap, and because conducted loss rises steeply with stored energy the design point read as needing **90.6 MW against 50**. Two earlier goals had carried that violation as "not a defect" and left it visible rather than fitting it away.

Goal `stored-energy-basis` asked whether the printed 504.65 MJ was the right target. Before the goal was even ratified, the agent scaled the stored energy to the printed value inside a copy of the oracle: the requirement fell to 37.5 MW and the verdict flipped. But the same arithmetic showed no reading of the paper's own plotted profiles reaches 504.65, and the paper's printed beta implies 567 MJ. The learning, accepted by a fresh reviewer and now an invariant in every later goal: **the printed value is not a target** (L-002). Round 1 registered the same author's systems-code papers, applied their definition of stored energy with the paper's own profile rules, and got 518.3 MJ. The gap decomposed: 5.3 points from the helium-ash profile shape (the model gave the ash the fuel's flat profile; the paper's rule peaks it in the core), 1.2 from profile exponents, 2.7 the paper's own and not closable from any admissible source.

The owner chose the fix over a footnote: *"we should fix the ash profile (and make sure this scales up for larger stellarators). and I don't want to add the footnote."* Work item WI-042 landed the ash on the paper's own rule, computed at every lever point rather than held as an exponent (the exponent comes out 4.73 at 10 keV, 4.05 at 14.63, 3.46 at 20). # 4. 1costingFE solves for the plant; this model computes the plant as chosen and then judges it

1costingFE (`~/1cfe/1costingfe`, package `costingfe`) is a JAX-native costing library: hand-written cost formulas over per-concept YAML defaults for 17 confinement concepts and four fuels, cost accounts CAS10 through CAS90 with CAS22 sub-accounts, autodiff sensitivities, and a `forward()` that solves the plant size from a requested net electric power (`model.py:612`, `tokamak_size_from_power`). It is the engine behind 1cFE's published numbers. Its own introduction names the structural gap: *"the framework takes power and geometry as two separate inputs... nothing enforces that the geometry you specify can actually deliver the power you ask for."* (`docs/blog/3 Intro/1costingfe-intro-post.md:172`.)

The owner's framing of the difference, verbatim: *"Whereas most custom TEA tools like 1costingFE need to decide 'what are the inputs' and 'what gets derived' (which can then be painful to change later), this is totally generalized to forward-pass and assess only. Not necessarily 'better', just has its own pros and cons."* (`stellarator-mbse-demo.md` § Owner's Words.)

In code that exists today, "forward-pass and assess" means three things. Levers go in and everything else is derived, so any lever can become a study axis without re-plumbing. Viability is asserted, not solved for: the ten verdicts answer "does this design work?" as data, where in 1costingFE the analyst answers it by eyeballing the LCOE. And the model is allowed to contradict its source and say so: under the model's chain the paper's operating point needed 90.6 MW where the paper says zero, and the modeler disclosed that at the assert site instead of tuning (§ 3). The trade is real: the handshake below required *feeding* this model a solved point, which is exactly the capability forward-pass gives up.

**The handshake proved the machinery, then the owner released it.** Demo criterion 3 required the forward model, fed the plant point 1costingFE solved for (stellarator, D-T, 1000 MW net, availability 0.9, 30-year life, 8-year build, 7 % interest, NOAK), to reproduce its per-account costs within a relative deviation of 1e-6. Measured, against 1costingFE commit `0254385`: 28 of 32 accounts pass; the magnet account is 2,129.9527 M$ on both sides, deviation −5.44e-10; LCOE 123.7430 (1costingFE) against 123.7289 $/MWh (model), a −1.14e-04 miss (`exploration/stellarator_e2e/HANDSHAKE_REPORT.md`). The miss decomposes exactly into two named remainders: a 0.72 M$ vacuum-pump sub-account the model omits by documented simplification, and an interest-during-construction convention the owner ruled on rather than matched (+2.2 % on the annual capital charge). The other four misses are the first remainder propagating downstream. Verdict: met.

On 2026-08-30 the owner closed it: *"I'm done caring about the 1costingFE reproduction. we showed we could do it. pin it, or archive those models. but let's move on — I do not want to be anchored to 1costingFE."* The verdict stands at commit `f22bd288` and is no longer a live gate; 1costingFE remains the validation reference where a comparison applies and is *never a limit* on what the model may contain (`STUDY_POLICY.md` § 10, owner 2026-08-21). Had the reproduction stayed a standing duty, every later step in which a typed-in number became a calculation would have been a regression against it.

# 5. Four repositories turn a text description into a sealed program, run it, and keep the paperwork

The four repos are a chain. Two of them (`agentic-mbse`, `sysml-codegen`) are named in the published post; `teax` and the layers inside `fusion-tea` are what the post's promised "TEA pipeline" post would describe.

**`agentic-mbse` gets sources in and checks the description before anyone compiles it.** Two problems sit at the front of the pipeline. Papers arrive as PDFs, and a number you cannot trust the extraction of cannot be cited; and a SysML model can be wrong in ways that only a checker sees. The toolkit's extraction pipeline (`src/agentic_mbse/extraction/`) is multi-pass and quality-gated, routing pages whose math or tables garbled to Claude re-extraction under a dollar budget (`quality_gate.py:416`). Its validator runs six levels, named in the source: 1 Syntax, 2 Structural Completeness, 3 Dependency Integrity, 4 Constraint Coverage, 5 Traceability & Documentation, 6 Architecture & Pipeline Readiness. Its `pm/` module owns the modeling project's state (`work/BACKLOG.md`, work items `WI-XXX`, insights `DI-XXX`, validation rows `SV-XXX`). One rule worth knowing: `sysml/syside_adapter.py` is the only place that may import SysIDE, the commercial SysML v2 parser. On a normal day here, a research subagent extracts a paper and then reads the *page image* for any table, because the Stellaris paper's extracted tables are corrupted in every row research checked (`burn-control/goal.md` § Invariants); a modeling agent runs `uv run agentic-mbse validate models --complete` after every edit.

**`sysml-codegen` compiles the description into a sealed program.** A SysML model describes; it does not run. The compiler parses the model tree, elaborates it into one node per modelled value, projects that into a computation graph, and renders Python. Three properties matter for everything downstream. First, the graph is ordered by a hand-written Kahn topological sort, and a cycle is a typed refusal, `SI_EDGE_DANGLING: typed module dependency cycle` (`elaboration/project.py:1197-1203`); there is no Newton step, relaxation, or convergence loop anywhere in the generator (§ 6). Second, a calc the expression compiler cannot lower becomes a `raise NotImplementedError` stub listed in `IMPLEMENTATION_BACKLOG.md` under "Stage 1: Implement Calculation Functions", for a person to implement once; on regeneration, each handwritten file's `run_*` signature (`FunctionSignature`: name, input type, return type, referenced fields, `generation/preservation.py:19-31`) is compared with the new module's, and the file is reported `Preserved`, or backed up to `handwritten/backup/` and `Regenerated`. Third, the package carries two SHA-256 fingerprints: `semantic_fingerprint`, over the canonical model contract (parameters, outputs, constraint catalog), and `executable_fingerprint`, over the sorted `path:hash` lines of every sealed file (195 in this package); a `verify.py` emitted into `contracts/` checks the seal on load and reports `TAMPER`, `MISSING`, `EXTRA`, `NAME_MISMATCH`, or `SEAL_MISSING`. This package: 72 module files, 60 handwritten implementations, 81 module declarations in `pipelines/pipeline.yaml`, 7 JSON input groups (the stellarator's group alone has 143 keys), generator 0.1.1, runtime contract 2.0.0.

**`teax` runs the program many times and keeps the evidence crash-safe.** Its `simkit` package (`~/1cfe/teax/packages/teax-simkit`) loads a sealed package through its own `verify.py`, evaluates points, and writes a SQLite store with write-ahead logging and `synchronous=FULL`, a fenced lease, and content-addressed staging with atomic commit (`study/store.py:106-107, 339`). A `StudyDefinition` carries three fingerprints (executable, model contract, and its own), and a store bound to one refuses another with `IncompatibleStore` (`store.py:151`); results are never merged across executable fingerprints (`query.py:9`, INV-5). `StudyRunner` runs one fixed order: validate, bridge, evaluate, assess, stage, commit (`runner.py:1-2`). Per point it records a frozen `ModelEvidence` with `responses` per constraint, `outputs`, and `provenance` that deliberately excludes wall-clock time (`evaluation/evidence.py:96-125`); the headline map turns `full_satisfaction` into `satisfied` and `violation` into `violated`, and a package with no constraints at all gets the disposition `unconstrained` from the study policy (`study/policy.py:131`). By documented intent, `teax` never imports a generated class; it reads a report through a few duck-typed attributes (`docs/evaluation-and-study.md:13`).

**`fusion-tea` holds the model, the package, the studies, and the two operating procedures.** The canonical SysML lives in `models/library/` (concept-agnostic: `foundation/`, `cost_structure/`, and the 13 analysis files in `analyses/`, which carry every calc and every constraint def) and `models/designs/stellarator_09/stellarator_plant.sysml` (1,311 lines, the Stellaris instance). A byte-identical twin at `exploration/stellarator_e2e/models/` is what the compiler actually reads, and `tests/models/test_model_family_spines.py` fails on any drift. The generated package is `exploration/stellarator_e2e/generated/` (reached as `pkg/stellarator_tea`); the studies sit beside it; `verify_stellaris.py` is the **oracle**, a hand-written pure-Python recompute of every formula that never imports the generated code. `scripts/study/` holds the generic study tools and `scripts/integrate.py` the seam (§ 7). The two procedures, `run-study` and `run-goal`, are skills under `.claude/skills/` whose rulebooks are `modeling_project/STUDY_POLICY.md` and `work/orchestration/GOAL_RUNBOOK.md`.

**How agents and programs divide the work.** The records follow one rule. Programs do the mechanical, fail-closed work: compute digests, refuse mismatches, execute points, derive verdicts, recount. Agents do the arguing, in files a stranger can audit: ground goals, write task scopes, choose windows, read records, propose what a finding means. Fresh agents check the arguing: a pre-execution critique of a study's framing, an administrator's recount of a record, a checkpoint on proposed dispositions, a review of a closed round. The owner rules on policy and on the gates he keeps: the no-fallbacks rule, the hold-out seal, the axis rule, merge, push, close.

**Visual cue:** four boxes in a row (extract and validate; compile and seal; run and store; model, study, goal) with three rows under each: the problem, the parts, a normal day.

# 6. The program is a DAG, so it cannot solve a loop; the modelers work around that with a ladder

A DAG (directed acyclic graph) means every value is computed once, in dependency order, with no cycles. That is what the Kahn sort in the compiler enforces and what the runner executes. It buys determinism, provenance, and speed. It costs the ability to close a loop.

Fusion physics is full of loops: confinement time depends on heating, heating on losses, losses on stored energy, stored energy on confinement. A systems code like PROCESS closes the power balance as an equality and solves. A DAG cannot. The owner raised the concern on 2026-08-02 and ratified the answer whole on 2026-08-21 (`STUDY_POLICY.md`), with an explicit intent to reach the demo on the delivered toolchain rather than adopt a relational solver.

The policy rests on one observation: inequalities and equalities do different things to a swept space. An inequality cuts away a region but leaves the survivor full-dimensional; every feasible point still has feasible neighbours, so inequalities accumulate safely. An equality asserted over swept inputs drops the feasible set's dimension by one; a grid never lands on the thin manifold, the verdict column reads nearly all violated, and the sweep carries no information. So the rule is: assert limits as inequalities (all ten are), and put equalities *inside* the forward computation, where they hold by construction at every point.

Two more rules follow. The **axis rule**, in the owner's words: *"it should be justifiably the causal DESIGN parameter. E.g. choose all geometry and input powers, and get an output power."* Sweep only levers an engineer chooses, never a computed quantity; and when a refinement turns a former lever into a computed value, the study executor stops sweeping it. And a **resolution ladder** for cycles, agent-proposed and owner-ratified:

- **R1, re-examine causality.** Many "cycles" are a lever plus a margin. The designer specifies on-axis field, so coil field is downstream, and "can the conductor deliver it?" enters as an inequality.
- **R2, collapse algebraically.** Pump power proportional to thermal power, and thermal power including recovered pump heat, isolates in one line; write the closed form flat.
- **R3, merge the cluster.** When the coupling is genuinely simultaneous, redraw one calc def whose inputs are the cluster's levers and whose outputs are the consistent tuple, with the solve in a handwritten body and its closure residual exposed for a thin guard assert. The confinement chain does this: `'Plasma Sustainment'` takes `n_e0`, `T_i0`, geometry, field and sourced constants, and returns the confinement time, the radiated powers, the ash and fuel densities and `p_aux_required`, with a damped fixed-point iteration for the ash inside the handwritten body (`mfe_plasma_sustainment.sysml:4-222`).
- **R4, seed and band.** Break a weak loop with a coarse lever-derived estimate and assert a validity band around it.

If the ladder runs out, the modeler records the cycle in a tripwire table rather than working around it; that record is the evidence a relational solver would need. The table is empty today (`STUDY_POLICY.md` § 8). Barred outright: a standing equality assert over swept axes, hand-rolled outer solve loops in study scripts, sweeping a computed quantity, sweeping a subset of an attribute's entry keys.

**The consequence you can see in the record.** Because the model computes *required* heating forward instead of solving for temperature, "is this an operating point?" became two inequalities on one operand (§ 3). A solved-temperature form was tried in goal `operating-point-closure` and rejected: no stable feasible burn exists inside the limits at the baseline, and the paper's own point sits on the unstable branch (that goal's L-002, reviewer-accepted).

**Visual cue:** the calc network sketched left to right (levers; `field_calc`; `sustain`; `beta_calc` and `wall_load`; the ten verdicts; `lcoe`) with a red cross over a would-be back-edge from power balance to confinement, and the ladder R1 to R4 as four rungs beside it.

# 7. A model change is proved, not trusted: digests, pins, the seam, and immutable records

The problem: a SysML edit invalidates everything downstream, the package, the studies that ran on it, the goal readings that cite them. The designers' answer is a chain of content digests and a fixed-point proof, not a staleness marker.

**Five digests tell a reader exactly what ran.** Two come from the compiler (§ 5): the semantic fingerprint (`baab7e4c…` at the current pin) and the executable fingerprint (`cd2c1c4a…`). One is `fusion-tea`'s own: the **indicator-input fingerprint**, the digest of the nine files the reachability tracer reads (`contracts/model_contract.json`, the seven `inputs/*.json`, `pipelines/pipeline.yaml`; recipe `indicator-input-fingerprint/v1` in `studies/manifest.json`). That one is **the pin**: `1d4a06b0e0e9…` today. A fourth, the effective executable fingerprint, folds in any files a study route was allowed to modify, and for the stock route degenerates to the sealed value. The fifth is the teax checkout's git revision (`8d877460…`), which no producer records, so the seam compares it against an argument and files the gap. Promoting a pin fixes what "the model" means for a study so that two results are comparable; a goal round has at most one.

**A model change obliges four steps before anyone may study it**, observed in WI-041, WI-042 and WI-043 and done by the item's own agent. Write the **restatement** (what every column of every committed study will mean under the new package, and the promise that no record is edited) and commit it *before* regenerating, so the git order attests the sequence. Regenerate in place with `--smart-regen --preserve-handwritten` and read the stencil line. Re-derive every pin and hand-patch none: the instance-graph snapshot, the entry-point census (`tests/models/data/mfe_census.json`, stamped against a semantic fingerprint; a test says "model meaning moved, re-derive" when it lags), the six known-answer fixtures, the manifest's fingerprints and baseline, the oracle mirror whenever a held input changes. Run the batteries: the six validation levels, `tests/models`, `tests/study`, and the single runner bit-exact against the oracle.

**The integration seam proves a package is a fixed point; it performs nothing.** `scripts/integrate.py` answers one question: is there exactly one verified, study-ready candidate for this package, and if not, what stopped it? It re-runs every producer *in place* and requires each to change nothing: regeneration must move zero bytes outside `handwritten/`, the recaptured snapshot must equal the tracked file, the manifest's pin must recompute to the recorded value. Ten gates in the producers' order: pinned packages, teax revision, regeneration, handwritten preservation, census and snapshot, model-family spine, manifest, preflight, verification (oracle parity, every verdict re-derived from the catalog's predicate), lineage. It returns `CANDIDATE` (exit 0) with the pin and both fingerprints, or `BLOCKER` (exit 1) naming the one producer and whether it *refused* or *could not run*. It commits nothing, and byte movement is judged by its own per-file digests because git reports clean inside the gitignored workspace where it runs (ADR-0009). The rule the round agent carries: a refusal at regeneration means the modeling item is unfinished, not that the seam is broken.

**Committed records are immutable; a stale reading is re-executed, never edited.** A study record is corrected only by appending `## Addendum <date>`, which may correct the record's *statement* of a fact and may never alter `snapshot.json`, `indicators.json`, or `results/`; a changed snapshot value is a different study with a new id (`record-template.md` § Immutability). A stale reading is restated by running a new study at the new pin over the same arms and joining every point to the committed record by case id (both 20260905 and 20260907 do this). The discovery log is append-only, goal files are append-only with dated `### Amendment` entries, and digest citations in goal artifacts are read by people, not compared by any procedure; that machine check waits on the hardening path until a real run shows the human reading failing (ADR-0003).

**The oracle is the one non-circular check, and it is demo-scoped.** It caught the first live case where the model moved and the mirror did not: when WI-033 set `p_pump` to 195 MW, the oracle still computed the old plant, 38 channels disagreed, and the verification gate refused (ADR-0010). The policy says the oracle retires from the study contract after the first two studies; the runbook and every study since still use it (§ Judgment).

**Visual cue:** a timeline of one model change: commit A (restatement) → commit B (regenerate; three fingerprints move; snapshot, census, fixtures, manifest re-derived) → `integrate.py` (ten gates, zero bytes moved) → `CANDIDATE` pin → new study joined to the old by case id. Beneath it the "never" list: never edit a committed record, never hand-patch a census, never tune.

# 8. A study is one sweep whose record a stranger can audit

The skill's own definition: *a study runs a model package over a set of parameter points and records what the model's own objective and constraints did at each one. What makes it a study rather than a sweep is the record: one directory that a second agent, with no memory of the run, can read and recover what was asked, what was assumed, what came out, and what none of it supports* (`.claude/skills/run-study/SKILL.md`).

**Three roles, one at a time.** The **user** sets the intent and rules on any axis the model turns out not to resist. The **executor** works the runbook and commits the record. The **administrator** reads *only* the committed record directory and writes `synthesis.md`, reporting a missing fact as missing rather than recovering it from elsewhere. Two modes: `execute` (intent, no record) and `administer` (record, no synthesis).

**The record splits values from arguments.** `exploration/<pkg>/studies/<YYYYMMDD-slug>/` holds `record.md` with seventeen fixed headings (among them intake verbatim, objective and result, constraint outcomes by qualified id, framing as proposed and as judged, indicators and rulings, preflight, window provenance, verification, review outcomes, findings, snapshot, and what the record does not contain), `snapshot.json` (every resolved value and digest: the three fingerprints, `arms[]` with their windows and verification, `stores[]` with the teax compatibility tuple, the teax revision, and the joined committed record's file digests), `axes.json`, `indicators.json`, and `results/`. A checker parses the snapshot; a person reads the record; neither restates the other. `tests/study/test_records.py` fails on an unreplaced placeholder and on a finding without its discovery-log row.

**The executor works fifteen steps, and only mechanical conditions stop the study.** In order: capture the intake verbatim; declare each axis as a complete entry-key group (a *tie* is declared, never derived: `magnet__R0` rides with `R` because they are the same physical radius); run the indicators for every proposed axis, declined ones included; argue the framing (`search` expects a boundary, `sensitivity` expects a monotone response and makes no boundary claim) and submit it to a pre-execution critique before any point runs; load the route and run the pinned baseline; run six preflight gates (declared keys, suffix siblings, identity, baseline headline reproduces, manifest and package fingerprints agree, package git-clean); scan the range with the oracle and fix the window, re-reading an inherited window's edges at the new package (a rule the owner added on 2026-09-06 after the 20260905 critique); choose and justify the route; run every point through the stock teax lifecycle with no hand-rolled loop; verify a verdict-stratified sample against the oracle, re-deriving verdicts from the operands; judge the framing against the result; record the review outcomes as named lenses; write the report, every number recomputable from `results/`; register findings and append discovery-log rows; resolve the snapshot and commit. "Fails closed" means the study stops only on a missing key, a fingerprint mismatch, an unparseable artifact, or a dirty package. A boring axis or a surprising result never gates; the executor records and argues it.

**Indicators give a sound negative and never a positive claim.** `scripts/study/indicators.py` digests the nine pin files and traces a deliberately over-approximate graph. `no_constraint_response` therefore means nothing in the model pushes back on this axis, which the owner reads as *"a signal the model is underdeveloped"*; it forces a user ruling before execution and a model-development finding the ruling does not discharge. `constraints_reachable` is only a possible path. Four things no indicator can derive, and every record says so: monotonicity, identity of one quantity across different key names, and dependency between operands inside one module.

**What a real record measured.** `20260905-stored-energy-basis`: 15 declared keys across 14 groups, 7 of them declined and held; preflight 6 of 6; verification 20 rows stratified over every verdict combination the study produced, 13 channels within 1e-9 (worst 4.25e-16), 9 verdicts re-derived, none disagreeing. The administrator's independent recount agreed with every headline count, transition, flip, optimum and margin, and found seven slips in the prose, none changing a conclusion: where the 28 newly excluded points sit in density; which of the 13 ignited design-column points sit at 16 MA and above (11, with 2 on the ash transect at 15.4 MA); a rise quoted as "+2.8 % at every point" that is a mean of +2.57 % over a range of +1.24 to +4.26; a stored-energy ratio range quoted from one column rather than the window; where 145 points with rising stored energy sit; an electron-exponent range of 0.406 to 0.450 rather than 0.44 to 0.5; and which limits catch the minor-radius transect at 1.3 (sustainment and beta, not sustainment and the wall). They landed as the record's first addendum (`synthesis.md` § 3.16).

**Visual cue:** the fifteen steps as a ladder, each rung labelled with what it deposits, gate icons on the six rungs that fail closed; beside it three swimlanes for user, executor, administrator.

# 9. run-goal pursues one question in bounded rounds that a fresh agent reviews

The skill's definition: *a goal is a grounded question pursued in rounds. A round is one agent's bounded attempt at one strategy, running one task at a time through the native workflows, ending in a mandatory written result and a review by a fresh agent who did not do the work* (`.claude/skills/run-goal/SKILL.md`). The operator and the round agent, writing in the goal files, decide what to work on next and what the evidence means. They do no work in those files; the work happens in the modeling PM, the research seam, and the study runbook, and the goal files cite those artifacts and never restate them, so nothing can disagree.

**Five files hold a goal.** `goal.md` (the question, written once with the operator), `trail.md` (what happened and what was decided, append-only), `learnings.md` (what this run now knows; the round result proposes, the fresh review accepts), the runbook (how), and the ADRs (why). `tests/orchestration/test_goal_contract.py` checks the headings and writer ownership and that no goal file cites the narratives directory, which is a presentation layer.

**A goal authorizes nothing until five field classes are filled**: grounding evidence (repo paths for what is already known), the answer contract (`§ Answered when`, concrete enough that two people agree), invariants (so "better" cannot drift), limits (retry cap 2, checkpoint revision cap 2, round limit 6 by default, restated in every goal), and reserved gates. A goal hollow in any class authorizes no task. The owner hardened that rule on 2026-08-27 after a five-session probe measured cold agents running full tasks on goals missing invariants or limits. The burn-control goal's invariants show what the class holds: the package identity entering the goal; "nothing is tuned"; "driven" keeps its definition so counts compare by case id; the printed 504.65 MJ is not a target; the clean room binds; a missing input is surfaced with options, never defaulted.

**A round runs one strategy, with no task list, and closes on one of six triggers.** The round agent opens with a `### Strategy revision` (approach, assumptions, abandonment conditions, intended model increment, intended study question) and no future task list, because a plan written before the evidence is authority granted in advance (ADR-0001). A round is bounded to at most one promoted pin and one committed study. It closes on exactly one of: a valid study reading, adverse ones included; a strategy blocker; changed comparison meaning; an unresolved owner gate; a declared limit; the goal answered. An honest empty round is a result.

**A task is scoped before it starts and returns one of six outcomes.** Six lines of scope (Objective, Why now, Scope, Inputs, Done when, Stop when), then a one-line start entry before the first side effect so an interruption leaves a trace, then the work through a native workflow, then a return: `COMPLETE`, `BOUNDED_NEGATIVE` (a real, useful no), `PREREQUISITE` (discovered, never predicted), `STRATEGY_BLOCKER` (closes the round), `OWNER_GATE`, or `MECHANICAL_FAILURE` (retry permitted only with identical task, inputs, scope and meaning). Every goal-level decision carries five fields: the trigger, the decision and reason, the tier (`execution detail | reserved gate | premise surprise`), who decided, what changed. A task invokes one of five **native seams** and reads what it returns: `research`, `model`, `integrate`, `study.execute`, `study.read`.

**Two fresh checks sit at two moments.** "Fresh" is the owner's word and a *session* boundary: *"The critic is never the author's session."* The **pre-execution disposition checkpoint** comes after a study reading proposes dispositions and before any follow-up executes; each resubmission is a new `C-00N.rK` entry, and hitting the cap writes a recorded stop and never permits execution. The **fresh round review** comes after close, over the whole round: every citation resolves, strategy fidelity, every task scope, retry honesty, every touched discovery-log row dispositioned, the learning delta; verdict `PASS | FINDINGS | OWNER_GATE`. An agent that cannot start a fresh session stops and hands back with a `### Stop` of kind `handoff`; it never reviews its own round.

**The owner keeps the gates, and the round owes every touched finding a home.** Merge, push, item close, archive, and every reserved gate are owner-held. Every discovery-log row a round's evidence touches gets a disposition (`model fix | research | declared seam | upstream filing`), appended under the same `<study-id>#<n>` id, never editing the sighting; no touched row returns `unrouted` (ADR-0004). You can watch this happen in `DISCOVERY_LOG.md`: row `20260905-stored-energy-basis#1` is sighted on 2026-09-05 as "the committed window's driven set ignites" with disposition "model fix, open, not minted", and a second row under the same id on 2026-09-06 reads "captured: minted as WI-043".

**The round as it actually ran, burn-control round 1.** Ground (two evidence deposits, six facts, one proposal, the owner's ratification). Open with one strategy: land the second inequality first, then measure. T-001, seam `model`: WI-043 through `/spec-model`, `/design-model`, `/plan-model`, `/implement-model`, returned `COMPLETE`. T-002, seam `integrate`: `CANDIDATE`, ten gates, the pin. T-003, seam `study.execute`: staged, critique returned. Then the run, the administrator's synthesis, checkpoint C-001, the disposition rows, the round result, the fresh review, and the owner's ruling on the restated design point.

**One premise surprise, handled the way the rules require.** The goal's fact 5 said the whole 13 to 18 keV window sits on the falling branch of the ignition curve, driven points included. The pre-execution critique probed 140 committed fence-feasible points and found 14, all driven, at 17 to 18 keV and low density, on the rising branch; the grounding probe's nine points had none at that corner. The round agent wrote a dated amendment to `goal.md` narrowing the fact; the hold argument stands because it never rested on the branch; the model's doc text that repeats the broad form was routed to a follow-on item and *not* corrected by the study; and the record states the expected branch pattern before any point runs and will measure the column as it is. An agent was wrong on the record in a way that stays visible, dated, and separable from what still stands.

**Visual cue:** nested boxes. Outer, the goal (question, answered-when, invariants, limits, reserved gates). Inside, rounds. Inside a round, tasks (scope → start → native work → return). Two gate icons for the checkpoint and the review; arrows out to the five seams.

## B. Glossary of the project's own words

- **Lever / entry point / entry key.** A value a study may vary, qualified like `stellarator_09__stellaris__T_i0`; 205 in the package. A **tie** declares that two keys are one physical quantity.
- **Channel.** A computed output; 113. The **headline** is `stellarator_09__stellaris__lcoe_calc__lcoe`.
- **Verdict.** `satisfied | violated | indeterminate`, per asserted constraint, per point.
- **Fence.** The records' word for an inequality limit that catches an edge of a window.
- **Driven / ignited / feasible.** Driven: every fence satisfied and `p_aux_required ≥ 0`. Ignited: `p_aux_required < 0` (two senses in the records, the bare column and negative-with-every-other-fence-satisfied; every claim says which). Under the ten-verdict package "feasible" equals the committed "feasible driven" by construction.
- **Fingerprint.** A SHA-256 digest that names content; five kinds (§ 7). **Pin.** The indicator-input fingerprint a study runs against; one promoted per round.
- **Seam.** A documented boundary a goal task invokes with a fixed input and return; five (§ 9). The **integration seam** is `scripts/integrate.py`.
- **Oracle.** `verify_stellaris.py`, an independent recompute of every formula; oracle-side diagnostics are never package evidence.
- **Census.** `tests/models/data/mfe_census.json`, the entry-point count and classification derived against a semantic fingerprint.
- **Restatement.** The pre-regeneration note saying what every committed study column will mean under the new package. **Addendum.** The only way a committed record is corrected.
- **Fresh.** A session that did not do the work; the owner's definition.
