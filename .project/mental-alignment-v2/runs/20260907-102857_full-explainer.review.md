## Findings

1. **The section sequence mirrors the owner's coverage list almost item-for-item.** After the TLDR and the "one mental model" section, the headings run: `Why this exists` (objectives/why) → `The thread that makes it real` (worked example, moved early) → `What makes this different from 1costingFE` (item 2) → `The four repositories and what each one is for` (item 3, capability map) → `The generated package is a one-way calculator` (item 4, DAG limits) → `Managing model updates` (item 5) → `A study is a question with a record` (item 6) → `run-goal is the loop that decides what to do next` (item 7) → `How to navigate the codebase` (item 8, structural) → `How the pieces flow together` (item 9, behavioral) → `Why this is non-trivial` (closing "why"/"worked examples" callback). Once past the opening thread, one section exists per requested bullet, in the bullet's own order. This is the exact failure the shared feedback names in "Coverage list used as the outline": "the sections 'follow almost exactly my "includes" list ... BUILD THE FUCKING MENTAL MODEL'" — and the writer prompt's rule that "Unless it explicitly specifies the sequence, define a logical narrative" and "A collection of accurate sections is not a synthesis." (cites: feedback/synthesis.md § "Coverage list used as the outline"; design_synthesis.md § "Define the narrative", § "One mental model")

2. **Several headings from the second half of the document name a topic rather than state the section's claim.** `## The four repositories and what each one is for`, `## How to navigate the codebase and the generated artifacts`, and `## How the pieces flow together: four behaviors` all describe what the section is about, not what it concludes — the same shape as the rejected example "The API exposes eight route groups for submitting, watching, and downloading jobs," which the feedback replaces with a heading stating the actual rule found inside the section. (cites: feedback/synthesis.md § "Heading that names what is present"; design_synthesis.md § "Clear on one reading" — "A heading states the section's real claim rather than naming a topic")

3. **Two headings stack several counted or listed phrases into one clause, making them hard to parse on first read.** `## Managing model updates: one item, one regeneration, one pin, and nothing tuned` chains four separate claims after the colon, and `## How the pieces flow together: four behaviors` names a bare count without saying which four in the heading itself. This is the pattern the feedback flags in "Heading that stacks counts and coined terms" (e.g., rejected: "One energy state under four linear constraints out-earns every other model tested") and in "Count standing in for the members" (e.g., rejected: "Four proof obligations remain, and MATLAB in Docker is the first — which four?"). (cites: feedback/synthesis.md § "Heading that stacks counts and coined terms", § "Count standing in for the members")

4. **The navigation section tells the reader how to read it instead of just being written that way.** `## How to navigate the codebase and the generated artifacts` opens with "Read this as a map of where truth lives, not as a file inventory," then proceeds as a directory-by-directory inventory anyway. The feedback's "Document as its own subject" entry says to delete this kind of self-describing sentence on sight rather than rewrite it, and if the section still reads as an inventory after the disclaimer, the disclaimer isn't doing the job the structure should do on its own. (cites: feedback/synthesis.md § "Document as its own subject")
