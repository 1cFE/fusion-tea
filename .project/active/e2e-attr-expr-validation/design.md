## Research Findings

### Current Solar Battery Generated Code Structure

The `generated/solar_battery/` directory contains a hybrid pipeline mixing hand-crafted and codegen-generated artifacts:

| Artifact | Location | Source | Regeneration Risk |
|----------|----------|--------|-------------------|
| Pipeline YAML | `pipelines/pipeline.yaml` | Hand-crafted | **OVERWRITTEN** by codegen |
| Module registry | `__init__.py` | Hand-crafted (includes ComponentCostEvaluator) | **OVERWRITTEN** by codegen |
| Run script | `run_pipeline.py` | Hand-crafted (project-root-relative paths) | **OVERWRITTEN** by codegen |
| ComponentCostEvaluator | `modules/component_cost_evaluator.py` | Hand-crafted | Survives (no codegen name collision) |
| Verify script | `verify_pipeline.py` | Hand-crafted | Survives (no codegen name collision) |
| `_impl.py` files (15) | `handwritten/solarbatterylibrary/` | Hand-crafted (3 implemented, 12 stubs) | Preserved by `--preserve-handwritten` |
| Module wrappers (15) | `modules/solarbatterylibrary/` | Codegen-generated | Regenerated |
| Schemas | `schemas/` | Codegen-generated | Regenerated |

**Critical finding**: Running codegen with `--smart-regen --preserve-handwritten` (without `--overwrite`) preserves the `handwritten/` directory and any files codegen doesn't generate by name. However, `pipeline.yaml`, `__init__.py`, and `run_pipeline.py` ARE generated by codegen and WILL be overwritten. These three files contain hand-crafted integrations that must be backed up and merged.

### Current Pipeline YAML Structure

The hand-crafted `pipeline.yaml` (`generated/solar_battery/pipelines/pipeline.yaml`) has 7 modules plus entry/exit:

```
entry_point → component_costs (ComponentCostEvaluator)
                ├─→ energy_production
                ├─→ annualized_om (receives p_net_kw from component_costs)
                ├─→ annualized_fuel
                ├─→ annualized_financial
                └─→ lcoe → exit_point
```

After Phase 2 regeneration, the key change is: `p_net_kw` will come from a synthetic module `solar_battery_plant__p_net_kw` instead of from ComponentCostEvaluator.

### Pipeline Channel Naming Conventions

From `pipeline.yaml`:
- MultiOutput channels use PQN format: `component_costs__total_capex`
- Downstream inputs extract floats via `.root`: `float component_costs__total_capex.root`
- Single-output modules produce named channels: `root: RootModel[float] annual_energy_mwh`

Codegen-generated computed attribute modules will follow ADR-004 naming:
- Module: `solar_battery_plant__p_net_kw`
- Output channel: `solar_battery_plant__p_net_kw__p_net_kw`

### Module Registry Pattern

`__init__.py` registers all modules including hand-crafted ComponentCostEvaluator:
```python
from solar_battery.modules.component_cost_evaluator import ComponentCostEvaluator, CostEvaluatorResult
# ... plus 15 codegen modules ...

def create_solar_battery_registry():
    return create_registry([ComponentCostEvaluator, ...], module_type_override={...})
```

After regeneration, codegen will overwrite this file WITHOUT the ComponentCostEvaluator import. The merged version must re-add it plus any new synthetic module.

### Execution Pattern

Pipeline execution requires `PYTHONPATH=generated`:
```bash
PYTHONPATH=generated uv run python generated/solar_battery/run_pipeline.py
```

### Existing Test Infrastructure

- `tests/conftest.py` provides `models_dir` and `load_sysml()` fixtures
- Model validation tests in `tests/models/` follow pattern: load model → check diagnostics → assert on elements
- Pipeline integration tests use `execute_pipeline()` from `simkit.core.pipeline`
- Expected system outputs in `models/tests/solar_battery/expected_system_outputs.csv`: LCOE=288.68, annual_om=160.0, etc.
- `verify_pipeline.py` checks 7 metrics with tolerance-based comparison

### Codegen CLI Behavior

From `sysml-codegen/src/sysml_codegen/cli/__init__.py`:
- `--smart-regen`: Compares function signatures in existing `_impl.py` files; preserves if unchanged, backs up and regenerates if changed
- `--preserve-handwritten`: Protects `handwritten/` directory from deletion when used with `--overwrite`
- Without `--overwrite`: Codegen writes new files over existing ones but doesn't delete non-colliding files

## Proposed Design

### Phase Execution Order

Phases B and C are independent of Phase A's merge output. Phase D depends on Phase A. Recommended execution:

```
Phase A (regenerate + merge)  ──→  Phase D (solar_battery TEAx)
Phase B (e2e_attr_expr model) ──→  (independent)
Phase C (regression suites)   ──→  (independent)
```

Phases A, B, and C can execute in parallel. Phase D is the only phase with a hard dependency on Phase A completion.

### Phase A: Regenerate Solar Battery

**Objective**: Verify Phase 1+2 codegen produces correct output for the existing solar_battery model.

#### Step A1: Backup Hand-Crafted Artifacts

Before running codegen, save the three files that will be overwritten:

```bash
cp generated/solar_battery/pipelines/pipeline.yaml \
   generated/solar_battery/pipelines/pipeline.yaml.pre-phase2
cp generated/solar_battery/__init__.py \
   generated/solar_battery/__init__.py.pre-phase2
cp generated/solar_battery/run_pipeline.py \
   generated/solar_battery/run_pipeline.py.pre-phase2
```

Also preserve the current IMPLEMENTATION_BACKLOG.md for comparison:
```bash
cp generated/solar_battery/IMPLEMENTATION_BACKLOG.md \
   generated/solar_battery/IMPLEMENTATION_BACKLOG.md.pre-phase2
```

#### Step A2: Run Codegen

```bash
cd ~/1cfe/fusion-tea
uv run sysml-codegen generate \
  --models models/tests/solar_battery/ \
  --output generated/solar_battery \
  --package-name solar_battery \
  --smart-regen --preserve-handwritten --verbose
```

Flags rationale:
- `--smart-regen`: Preserves `_impl.py` files that have unchanged signatures (the 3 hand-implemented ones: `energyproductioncalc_impl.py`, `annualizedfinancialcalc_impl.py`, `lcoecalc_impl.py`)
- `--preserve-handwritten`: Protects the entire `handwritten/` directory
- No `--overwrite`: Preserves `component_cost_evaluator.py`, `verify_pipeline.py`, and other hand-crafted non-colliding files

#### Step A3: Verify Codegen Output

Check these assertions against the codegen output:

1. **Auto-implementation (FR-A2)**: All 15 `_impl.py` files in `handwritten/solarbatterylibrary/` should now have `AUTO_IMPLEMENTED = True`. The 3 previously hand-implemented files may be preserved (signature match) or backed up and regenerated (if codegen produces different signatures with auto-impl). Either outcome is acceptable — verify the files contain actual computation code, not `raise NotImplementedError`.

2. **FORMULA synthetic module (FR-A3)**: The codegen-generated `pipeline.yaml` should include a module named `solar_battery_plant__p_net_kw` with `# source: computed_attribute` comment. Inspect the new `pipeline.yaml` to confirm.

3. **IMPLEMENTATION_BACKLOG (FR-A5)**: Compare new vs old. New version should show "0 functions to implement" (all auto-implemented).

4. **New module wrapper**: A new file `modules/*/solar_battery_plant__p_net_kw.py` (or similar codegen naming) should exist for the synthetic FORMULA module.

#### Step A4: Diff Review, Merge, and Rollback Plan

The codegen-generated `pipeline.yaml` will contain all codegen-discovered modules but will NOT include ComponentCostEvaluator. The hand-crafted hybrid must be reconstructed.

##### A4a: Diff Review (before merging)

Before any merge, diff the codegen-generated `pipeline.yaml` against the backup to understand the full scope of changes:

```bash
diff generated/solar_battery/pipelines/pipeline.yaml.pre-phase2 \
     generated/solar_battery/pipelines/pipeline.yaml
```

**Expected changes**: Addition of `solar_battery_plant__p_net_kw` synthetic module, possible module naming/ordering changes, channel naming updates.

**Fallback**: If the diff reveals structural changes beyond the synthetic module addition (e.g., changed module naming conventions, new schema types, different channel wiring patterns), document them in the report and reassess the merge strategy before proceeding. The `.pre-phase2` backups are the rollback path — if the merge produces incorrect results or the diff is unmanageably large, restore from backups and file a sysml-codegen issue.

##### A4b: Merge Strategy

Start from the saved `pipeline.yaml.pre-phase2` and apply the Phase 2 diff — inserting the synthetic module and rewiring `annualized_om.p_net_kw`. Use the codegen-generated `pipeline.yaml` as a reference for correct naming conventions.

**Changes from pre-Phase2 pipeline.yaml**:

1. **Add synthetic module** after `component_costs`, before `energy_production`:

```yaml
  # Computed attribute: p_net_kw = p_net_mw * 1000.0
  solar_battery_plant__p_net_kw:  # source: computed_attribute
    module_type: SolarBatteryPlantPNetKw
    inputs:
      p_net_mw: float component_costs__p_net_mw.root
    outputs:
      p_net_kw: RootModel[float] solar_battery_plant__p_net_kw__p_net_kw
```

Input source: `p_net_mw` from ComponentCostEvaluator (which reads it from `design_params.json`).
Output channel: follows ADR-004 naming `{module_name}__{attr_name}`.
Module type: PascalCase per ADR-004 (`SolarBatteryPlantPNetKw`).

2. **Rewire annualized_om.p_net_kw** from ComponentCostEvaluator to synthetic module:

```yaml
  # BEFORE:
  annualized_om:
    inputs:
      p_net_kw: float component_costs__p_net_kw.root    # From ComponentCostEvaluator

  # AFTER:
  annualized_om:
    inputs:
      p_net_kw: float solar_battery_plant__p_net_kw__p_net_kw.root  # From synthetic module
```

3. **Keep p_net_kw on ComponentCostEvaluator outputs unchanged.** The unused channel is harmless (pipelines don't error on unconsumed channels), removing it would require modifying `component_cost_evaluator.py`, and Phase 3 will eliminate ComponentCostEvaluator entirely. Not worth the churn.

##### A4c: Verification

Compare the merged `pipeline.yaml` against the codegen-generated version to confirm the synthetic module naming and channel conventions match. Specifically verify that the module type name, input/output channel names, and type annotations in the merged YAML are consistent with what codegen produced.

#### Step A5: Merge Registry and Run Script

1. **`__init__.py`**: Take the codegen-generated version and add back the ComponentCostEvaluator import and registry entry. Also add the new synthetic module if codegen generated a module class for it. Reference the codegen-generated `__init__.py` to see the new module imports, then merge with the ComponentCostEvaluator lines from `__init__.py.pre-phase2`.

2. **`run_pipeline.py`**: Compare codegen-generated version with saved backup. If the codegen version works (resolves paths correctly), use it. If it lacks the project-root-relative path resolution, restore the hand-crafted version. The key requirement is that `model_path` resolves correctly for ComponentCostEvaluator's `generate_costs.py` import.

#### Step A6: Document All Manual Adjustments

Create a section in the validation report documenting:
- What files were backed up
- What codegen produced (diff summary)
- What manual merges were performed (before/after diffs)
- Why each merge was necessary
- Whether each adjustment is temporary (until Phase 3 removes ComponentCostEvaluator) or permanent

### Phase B: E2E Attr Expr Model

**Objective**: Create a flat test model that exercises all 12 Phase 1+2 patterns, run codegen, execute TEAx, verify numerical outputs.

#### Step B1: Create SysML Model Files

Create `models/tests/e2e_attr_expr/library.sysml` and `models/tests/e2e_attr_expr/design.sysml` from the research document (Section "Phase B: New Test Model"). The model is defined there with:
- `E2EAttrExprLibrary` package: 4 CalcDefs (ComponentCostCalc, AnnualizedCostCalc, EnergyCalc, SimpleLCOECalc)
- `E2EAttrExprDesign` package: 1 part usage `e2e_plant` with 6 literal params, 6 FORMULA attrs, 4 CalcUsages, 1 EXPOSE_PURE alias

#### Step B2: Parse and Validate Model

```bash
# Parse check (FR-B2)
uv run syside check models/tests/e2e_attr_expr/

# Full validation (FR-B3)
uv run agentic-mbse validate models/tests/e2e_attr_expr/ --complete
```

Expected: Zero parse errors. No V2 violations on FORMULA attributes (agentic-mbse FORMULA exemption). L8 codegen readiness pass.

#### Step B3: Run Codegen

```bash
uv run sysml-codegen generate \
  --models models/tests/e2e_attr_expr/ \
  --output generated/e2e_attr_expr \
  --package-name e2e_attr_expr \
  --overwrite --verbose
```

`--overwrite` is safe here — this is a fresh generation with no hand-crafted artifacts.

#### Step B4: Verify Codegen Structural Output — Per-Pattern Checklist

Inspect the generated artifacts and verify each of the 12 spec patterns (FR-B9) maps to a specific codegen artifact:

##### Patterns 1-6: FORMULA Synthetic Modules

Each FORMULA attribute MUST generate a synthetic module with `# source: computed_attribute` in pipeline YAML. Verify topological ordering respects chains.

| # | Pattern | Expected Module Name | Expected Inputs | Topo Constraint |
|---|---------|---------------------|-----------------|-----------------|
| 1 | Simple FORMULA (`power_mw`) | `e2e_plant__power_mw` | `quantity`, `unit_cost` (entry points) | None |
| 2 | Chain FORMULA (`power_kw`) | `e2e_plant__power_kw` | `power_mw` (from module #1) | After #1 |
| 3 | 2-hop chain (`annual_om`) | `e2e_plant__annual_om` | `om_rate` (entry), `power_kw` (from #2) | After #2 |
| 4 | Simple binary (`area`) | `e2e_plant__area` | `length`, `width` (entry points) | None |
| 5 | 3-term FORMULA (`volume`) | `e2e_plant__volume` | `length`, `width`, `height` (entry points) | None |
| 6 | Fan-in FORMULA (`surface_cost`) | `e2e_plant__surface_cost` | `area` (from #4), `cost_per_sqm` (entry) | After #4 |

**Check**: Count synthetic modules in pipeline YAML — expect exactly 6 with `# source: computed_attribute`.

##### Patterns 7-8: CalcDef Auto-Implementation

| # | Pattern | Expected `_impl.py` File | Verification |
|---|---------|--------------------------|-------------|
| 7 | CalcDef 5-output auto-impl | `componentcostcalc_impl.py` | `AUTO_IMPLEMENTED = True`, 5 output expressions |
| 8 | CalcDef with `**` exponent | `annualizedcostcalc_impl.py` | `AUTO_IMPLEMENTED = True`, `**` in CRF expression |

**Check**: ALL `_impl.py` files have `AUTO_IMPLEMENTED = True`. IMPLEMENTATION_BACKLOG.md shows "0 functions to implement".

##### Pattern 9: EXPOSE_PURE

| # | Pattern | Expected Artifact | Verification |
|---|---------|-------------------|-------------|
| 9 | EXPOSE_PURE (`total_capex`) | NO module generated | `total_capex` does NOT appear as a synthetic module in YAML. The `financial` module's `total_capex` input wires to the `component_cost` CalcUsage output channel (alias resolution). |

**Check**: Grep pipeline YAML for `total_capex` — it should appear only as an input wiring, not as a module name.

##### Patterns 10-12: Cross-Module Wiring

| # | Pattern | Verification |
|---|---------|-------------|
| 10 | FORMULA→CalcUsage (`energy.power_mw`) | `energy` module's `power_mw` input wired to `e2e_plant__power_mw` module output (NOT entry point) |
| 11 | FORMULA→CalcUsage 2-hop (`lcoe.annual_om`) | `lcoe` module's `annual_om` input wired to `e2e_plant__annual_om` module output |
| 12 | CalcUsage→CalcUsage via EXPOSE (`financial.total_capex`) | `financial` module's `total_capex` input wired to `component_cost` module's `total_cost` output (resolved through EXPOSE alias) |

**Check**: For each wiring, the pipeline YAML input channel references a module output, not an entry point parameter.

#### Step B5: Execute TEAx Pipeline

```bash
PYTHONPATH=generated uv run python generated/e2e_attr_expr/run_pipeline.py
```

No manual pipeline adjustments should be needed — this is a flat model with no hand-crafted components.

#### Step B6: Verify Numerical Outputs

Create `generated/e2e_attr_expr/verify_pipeline.py` following the solar_battery `verify_pipeline.py` pattern. This script programmatically checks all 16 ground truth values from the research document (Section "Phase B: Ground Truth Values") with specified tolerances. This makes Phase B repeatable and supports NFR-2 (permanent regression test).

**Tolerance specification**:

| Category | Tolerance | Applies To |
|----------|-----------|-----------|
| Simple arithmetic | exact (0.0 relative) | power_mw, power_kw, annual_om, area, volume, surface_cost, material_cost, fab_cost, install_cost, total_cost, idiot_index, total_capex, annual_energy_mwh |
| Exponentiation | 1e-6 relative | crf, annualized_cost |
| Compound (multi-step float) | 1e-4 relative | lcoe |

**Ground truth values**: See research document Section "Phase B: Ground Truth Values" for the canonical expected values table. The `verify_pipeline.py` script MUST encode all 16 values with the tolerances above.

**Script structure** (following `generated/solar_battery/verify_pipeline.py`):
1. `EXPECTED_VALUES` dict mapping output channel names to `(expected_value, relative_tolerance)` tuples
2. `find_latest_output_dir()` to locate most recent pipeline run
3. `verify()` function that loads each JSON output, handles `RootModel[float]` serialization (`{"root": value}` or bare float), and compares against expected
4. Exit code 0 on all-pass, 1 on any failure

**Execution**:
```bash
PYTHONPATH=generated uv run python generated/e2e_attr_expr/verify_pipeline.py
```

**Note**: The exact output channel names will depend on codegen naming conventions discovered in Step B4. The verify script should be written AFTER inspecting the codegen output to use the correct channel names.

Expected values (from `verify_pipeline.py` and `expected_system_outputs.csv`):

| Metric | Expected | Tolerance |
|--------|----------|-----------|
| total_capex | 41205.0 | exact |
| annual_energy_mwh | 11.14272 | 1% |

**Key verification**: `annual_om_cost = 160.0` confirms the FORMULA→CalcUsage wiring works correctly:
- ComponentCostEvaluator provides `p_net_mw = 0.008`
- Synthetic module computes `p_net_kw = 0.008 * 1000.0 = 8.0`
- AnnualizedOMCalc receives `p_net_kw = 8.0` from synthetic module
- Computes `annual_om_cost = 20.0 * 8.0 = 160.0`

If `annual_om_cost` were still receiving `p_net_kw` from ComponentCostEvaluator (which reads 8.0 from `design_params.json`), the value would be the same. The distinction is structural (wiring source), not numerical. To verify the wiring is actually through the synthetic module, inspect the pipeline YAML and/or enable verbose logging during execution.

## Potential Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| Codegen overwrites `component_cost_evaluator.py` | High — breaks hybrid pipeline | Pre-verified: codegen only generates files for extracted CalcUsages. No CalcUsage named `component_cost_evaluator` exists. File survives without `--overwrite`. |
| `--smart-regen` backs up hand-implemented `_impl.py` files | Low — auto-impl replaces them | Backup files preserved in `handwritten/backup/`. Auto-impl'd versions should produce identical outputs. Compare if needed. |
| Codegen-generated `pipeline.yaml` uses different channel naming than hand-crafted version | Medium — merge difficulty | Inspect codegen YAML before merging. Use codegen naming conventions for the synthetic module (ADR-004). |
| Synthetic module's output type doesn't match pipeline's `RootModel[float]` convention | Medium — runtime type error | Inspect generated module wrapper. The solar_battery pipeline uses `RootModel[float]` (Float primitive). Codegen synthetic modules may use bare float. Adapt YAML accordingly. |
| e2e_attr_expr model triggers an undiscovered codegen bug | Medium — Phase B fails | This IS the point of Phase B. Document the bug, file it in sysml-codegen, and note as a finding. |
| `execute_pipeline()` API changed between codegen versions | Low — runtime import error | Use the codegen-generated `run_pipeline.py` as reference for current API. |

## Integration Strategy

This validation integrates with existing workflows:

1. **Permanent regression model**: The e2e_attr_expr model (`models/tests/e2e_attr_expr/`) becomes a permanent test fixture alongside solar_battery and coffee_maker.
2. **Updated solar_battery**: The regenerated `generated/solar_battery/` with auto-implemented CalcDefs and FORMULA module replaces the pre-Phase2 version.
3. **Validation report**: Documents the current state of Phase 1+2 features and remaining Phase 3 gaps, serving as a gate for Phase 3 planning.

## Validation Approach

### Automated Checks

Each phase has explicit pass/fail criteria:

- **Phase A**: File-level assertions (AUTO_IMPLEMENTED flag, module existence, YAML content)
- **Phase B**: Parse → validate → codegen → execute → numerical comparison (12 pattern coverage)
- **Phase C**: Existing test suite pass counts
- **Phase D**: 7-metric numerical comparison against established expected values

### Report Document

Results recorded at `.project/active/e2e-attr-expr-validation/report.md` with:
- Per-phase pass/fail summary
- Per-pattern results for Phase B (12 patterns)
- All manual adjustments documented (Phase A/D pipeline.yaml merge)
- Bugs discovered (if any) with sysml-codegen issue references
- Before/after diffs for all hand-merged files
