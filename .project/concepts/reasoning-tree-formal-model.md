# Formal Model of the Reasoning Tree

## The Problem Being Modeled

The fusion design space is context-dependent: each architectural choice changes what downstream questions exist. Phase 1 confirmed this empirically — 0/30 randomly sampled column combinations were physically coherent, N/A density reached 36.7%, and effective degrees of freedom were ~2 despite 18 columns. The table is a classification scheme, not a design space.

The reasoning tree explores this space by recursive decomposition from universal requirements. Its goal: derive the constraints that shape the design space from first principles — explain why certain combinations don't exist, and identify where knowledge transfers between concepts.

## 1. The Core Mechanism

The algorithm's atomic operation is an **expansion**. Inputs: **accumulated context** (the chain of design choices and their reasoning from root to this node), a **question** (the design decision to resolve), and **requirement lenses** R1-R6 (fuel supply, fusion conditions, net energy, energy extraction, nuclear environment, structural integrity). Outputs: **options** (viable approaches), **constraints** (what each option forces/eliminates/activates), **negative space** (non-viable approaches with physics reasoning), and **downstream questions** (new design questions each option creates).

The mechanism that produces all analytical work: **requirements are invariant; context changes.** R6 (structural integrity) is the same requirement at every node, but means steady-state divertor heat flux in a tokamak context and cyclic blast loading in an IFE context. The requirement didn't change — accumulated context determines what R6 demands. This is requirements decomposition as practiced in systems engineering, where the same top-level requirement decomposes differently depending on upstream architecture — except the algorithm generates the decomposition rather than hand-crafting it.

Accumulated context carries reasoning (thesis, requirement analysis), not just choices. Two paths arriving at the same sub-problem with the same context carry the same justification for being there: shared context = shared justification = transferable conclusions.

## Formal Ontology and Algorithm

### Objects

**Context entry** *c* = (*choice*, *reasoning*). A design decision paired with the analysis that motivated it — thesis, requirement-by-requirement assessment, trade-off structure. Context entries encode not just WHAT was chosen but WHY, which is what makes transfer analysis possible (two paths sharing context share justification, not just labels).

**Accumulated context** *C* = [*c*₁, *c*₂, …, *c*ₖ]. An ordered sequence of context entries from root to the current node. Append-only: entries are never modified or removed. *C* = [] exists only at the root. The path from root to any node uniquely determines its *C* — there is a bijection between tree paths and accumulated contexts.

**Requirement lenses** *R* = {R1, R2, R3, R4, R5, R6}. A fixed set, invariant across all expansions. Each *Rᵢ* is reinterpreted at every node through *C* — the same *Rᵢ* produces different demands in different contexts. This invariance-under-reinterpretation is the core mechanism (Section 1).

**Question** *q*. A design question to resolve, expressed as a natural-language string. The root question *q*₀ is manually authored. All subsequent questions are generated by the LLM as part of an option's *downstream_questions* output and selected by the navigator.

**Option** *o* = (*id*, *thesis*, *requirement_analysis*, *constraints*, *downstream_questions*, *context_addition*):
- *thesis*: what trade-off this approach navigates
- *requirement_analysis*: {R1: *a*₁, …, R6: *a*₆} — how this option bears on each *Rᵢ* given *C*
- *constraints*: [*κ*₁, …, *κ*ⱼ] — derived constraints (see below)
- *downstream_questions*: [*q*₁, …, *q*ₙ] — questions this choice creates that did not previously exist
- *context_addition*: a new context entry *c*′ to append if this option is followed

**Constraint** *κ* = (*condition*, *consequence*, *type*, *requirement_basis*, *reasoning*):
- *condition*: a partial assignment of design variables that triggers this constraint (e.g., `{fuel: D-T}`)
- *consequence*: what is forced, eliminated, or activated (e.g., `{neutron_shielding: heavy}`)
- *type* ∈ {force, eliminate, activate}
- *requirement_basis*: which *Rᵢ* drives this constraint
- *reasoning*: the physics/engineering chain justifying the implication

Each *κ* also carries provenance: *source_node* (where derived) and *justification* (the accumulated context *C* at derivation time). The condition and justification are distinct and serve different purposes: the **condition** determines where the constraint APPLIES (any branch whose context satisfies the condition). The **justification** records HOW it was DERIVED (the specific reasoning path). Transfer analysis uses conditions; validation uses justifications.

**Negative space entry** *ν* = (*approach*, *reason_non_viable*, *requirement_basis*, *context_dependency*). If *context_dependency* references entries in *C*, the exclusion is context-dependent (non-viable only given those upstream choices). If it references only physical constants, the exclusion is universal.

**Node** *N* = (*id*, *q*, *C*, *status*, *expansion*) where *status* ∈ {pending, expanded} and *expansion* holds the full output of the expand operation if expanded, null if pending.

### The Algorithm

```
INITIALIZE:
  q₀ ← manually authored root question
  T  ← { N₀ = (L0, q₀, [], pending, null) }
  K  ← ∅                                        // constraint registry

EXPAND(N) where N.status = pending:
  (options, negative_space) ← LLM(N.C, N.q, R)  // stateless — sees only (C, q, R)

  for each option oᵢ ∈ options:
    C'  ← N.C ⊕ [oᵢ.context_addition]           // append — context only grows
    q'  ← select(oᵢ.downstream_questions)        // currently: first element
    N'  ← (new_id, q', C', pending, null)
    T   ← T ∪ {N'}

    for each κ ∈ oᵢ.constraints:
      κ.source_node   ← N.id
      κ.justification ← N.C
      K ← K ∪ {κ}

  N.status    ← expanded
  N.expansion ← (options, negative_space)

ITERATE:
  Select pending nodes from T                    // currently: all at next level
  For each: EXPAND
```

The LLM call within EXPAND is a black box. The formalism specifies its inputs (*C*, *q*, *R*), its output structure (options, negative_space), and how outputs connect to the rest of the tree. It does not model how the LLM produces options or derives constraints — that process is generative and non-deterministic.

### Derived Concepts

**Convergence.** Constraints *κ*_A (branch A) and *κ*_B (branch B) converge when they address the same consequence variable from different derivation paths: *κ*_A.*consequence* ∩ *κ*_B.*consequence* ≠ ∅ while *κ*_A.*source_node* ≠ *κ*_B.*source_node*. Convergence is evidence the constraint captures real structure, not an artifact of one branch's reasoning.

**Transfer scope.** Determined by *κ*.*condition*. A constraint applies to any branch whose *C* satisfies *κ*.*condition*. Narrower conditions = narrower scope: `{fuel: D-T}` transfers broadly; `{fuel: D-T, confinement: compact_tokamak, magnet: HTS}` transfers only to compact HTS tokamaks.

**Pruning.** Branch *B* prunes at node *N* when EXPAND(*N*) → *options* = ∅ — all approaches fall into negative space given *C*_N. This has not occurred in the current tree; context at L0-L1 is too shallow to rule out any viable confinement family.

**Seeding.** A seed *s* is a context entry injected as *C*₀ = [*s*] at the root (replacing *C*₀ = []). All downstream expansions see *s* in their accumulated context. The seed changes: (a) which options survive at each node, (b) which downstream questions are generated, (c) which constraints converge across branches. The expansion mechanism is unchanged; the initial condition shifts.

## 2. Two Kinds of Output

The expansion's outputs differ in epistemological status.

**Negative space is analytical.** A deductive chain: this physics mechanism + this requirement + this context → non-viable. The chain closes and is verifiable. L0 excluded gravitational confinement (force ratio requires brown-dwarf mass) and beam-target (Coulomb scattering exceeds fusion cross-section by 10⁴). L1 produced four exclusions that are context-dependent — non-viable *only because* closed magnetic topology was chosen. Context-dependent negative space is the algorithm's core mechanism working as designed.

**Options are generative.** Informed by context and requirements but not deduced from them. Different runs could produce different option sets from identical inputs. Assessable for completeness but not for correctness the way negative space is.

**Constraints are intermediate.** Extracted from generative reasoning but independently checkable. "D-T fuel forces heavy neutron shielding" is true or false regardless of how it was derived. The constraint registry's value depends on validation — against the table, against cross-branch consistency, or against known physics. This matters because the algorithm's strongest analytical signal (negative space) is its most verifiable output, while the output most relevant to Goals 1-3 (constraints) is in this intermediate position.

## 3. What Controls Tree Shape

**Question specificity determines option count.** A broad question ("how to confine?") produces architecturally distinct options with different constraint cascades. A narrow question ("what mirror ratio?") produces parametric variants. Accumulated context determines specificity: more context → fewer remaining degrees of freedom → more specific questions → fewer but more differentiated options. L0 produced 5 options from an unconstrained question; L1 produced 3 from a question conditioned on one prior choice. This should continue — if option count fails to shrink with depth, the questions are broader than the accumulated context warrants. In concept design, this is the well-established progression from concept selection (few choices, large consequences) to detailed design (many parameters, local effects).

**Pruning requires constraint density, which requires depth.** A branch prunes when a requirement becomes definitively unsatisfied. At L0, only fundamental physics violations are catchable. At deeper levels, accumulated context activates requirements in increasingly specific ways. The tree necessarily broadens before it narrows because constraint density increases with depth. The 14 pending L2 nodes are not a failure — they reflect that two levels of context aren't enough to produce binding violations for any of the five viable confinement families. Whether a branch *eventually* prunes depends on whether the questions asked along it activate binding constraints — a question about magnet topology activates R6 in new ways; a question about control system software may not. Pruning speed is determined by question selection.

## 4. Navigation vs. Reasoning

The LLM fills two roles that demand different information.

**Reasoning** is local. The reasoner sees accumulated context, the current question, and R1-R6. It produces options, constraints, and negative space for one node. L0 and L1 demonstrate this working well.

**Navigation** requires global information. Which question to explore next depends on the tree's overall structure: what constraints exist across branches, where depth would produce the most constraint overlap, which requirements remain untested along each path. Currently, navigation is local — each option generates 5-6 downstream questions, the first becomes the child node's question, the rest are discarded. The navigator sees only what the reasoner within one option produced. In engineering practice, this is analogous to sequencing subsystem design in the order problems happen to come up, rather than following risk-driven or critical-path sequencing.

### What Goals 1-3 Ask, in These Terms

**Goal 1 (derive table columns from upstream choices)** asks whether the constraint cascade reproduces engineering classifications. Whether this happens depends on whether the tree descends to engineering-level decisions ("what magnet type?") or remains at physics-level questions ("what is the maximum achievable beta?"). Descent to engineering vocabulary is a precondition — and the current local navigator has no mechanism that favors descent over lateral exploration. But Goal 1 also has a deeper reading through the abstraction gap (Section 5): the constraints may EXPLAIN table columns rather than MATCH them, which changes the validation test.

**Goal 2 (context-dependent questions emerge)** tests whether different contexts produce different questions. This is already working: L0's five branches generate entirely different question lists (rotational transform vs. driver technology vs. compression method). The mechanism functions. What Goal 2 further requires: that the *right* engineering questions emerge within families — "ash handling" in laser IFE, "current drive" in tokamaks. These are more specific and only emerge at depth. Each option already generates 5-6 such questions; the information exists in the expansion output but only one question is followed. Whether the right questions are the ones selected is, again, a navigation problem — but the GENERATION of context-dependent questions is not the bottleneck.

**Goal 3 (seed with priors)** is a context manipulation. A seed ("cheap direct energy conversion exists") is a pre-committed context entry injected before the root. It changes which requirements are binding at every subsequent node — a "design-to" assumption that constrains the trade space before exploration begins. The model predicts that a seed changes which options survive (different constraints bind), which downstream questions are generated (different requirements dominate), and where branches converge (different sub-problems become shared). The reasoner's mechanism is unchanged; the constraint landscape shifts.

## 5. The Abstraction Gap

The algorithm reasons at the physics level (field topology, loss cones, compression ratios). The table classifies at the engineering level (Confinement Family, Magnet Type). All 22 L0 constraints are unmappable.

**The gap narrows through descent.** L0: "how to confine?" → field topology (no table column). L1: "how to provide rotational transform?" → tokamak vs. stellarator (approaching the table's MFE Topology column). Projected L2: "what magnet type?" → HTS vs. LTS (directly mappable). Question specificity forces vocabulary specificity — you cannot ask about magnet type without using magnet vocabulary.

**The gap may stabilize at an intermediate level.** The most analytically interesting constraints use physics variables applied to engineering concerns. "Disruption severity scales with stored energy per unit volume" combines MHD stability (physics) with plant availability (engineering). Neither the table's vocabulary (Operation Mode) nor pure physics (field topology) captures it. This intermediate vocabulary — physics-of-failure applied to engineering consequences — maps to real engineering practice, where physics-of-failure analysis and classification standards describe the same reality at different levels, bridged by causal explanation rather than vocabulary mapping.

**Consequence for Goal 1:** If the algorithm's strongest constraints live at this intermediate level, they would explain the table rather than reproduce it. "D-T fuel + closed geometry → neutron-flux-dominated energy deposition → thermal conversion is the only viable capture method" explains why the Thermal column appears without using the word "Thermal." Validation becomes: do the constraints logically entail the table's classifications? — a harder but more informative test.

## 6. Convergence and Transfer

The original vision: when two branches independently produce the same constraint, their overlapping context defines what transfers. "Must breed tritium" with justification `{fuel: D-T}` transfers across all D-T concepts. "Blanket space is limited" with justification `{fuel: D-T, confinement: compact tokamak}` transfers only within compact tokamaks. The justification set makes transfer scope explicit.

**This mechanism is designed but unexercised.** Branches run in isolation with no cross-branch memory. Only one branch has been expanded past L0. The five L0 branches reason about different physics (field topology, compression, electrostatics) with no shared constraint vocabulary at this depth. Convergence requires sufficient depth on multiple branches to reach shared sub-problems — a D-T tokamak and a D-T mirror should both encounter "breed tritium," but only if navigation on each branch reaches the fuel question. The closed-magnetic branch went to rotational transform at L1, not to fuel choice. Convergence is a function of depth × breadth × navigation choices.

Comparison across branches also requires infrastructure that doesn't exist: extracting justification sets, identifying shared consequence variables, and determining what's shared vs. context-specific. The constraint registry stores constraints per-node with no cross-branch query capability.

**Convergence as validation.** If two branches independently derive "D-T → thermal conversion," that convergence validates the constraint AND explains the table column — stronger evidence than either branch alone. Goal 3 (seeded exploration) would change convergence patterns: a seed like "cheap DEC" prevents thermal-conversion constraints from activating, causing branches that normally converge to diverge. The change in convergence patterns maps which engineering classifications are robust to the seed assumption and which are contingent on it.
