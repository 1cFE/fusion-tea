1. The Problem

A flat comparison table can't capture the fusion design space. Context changes everything.

When we built a morphological table of ~36 fusion concepts across 12 design dimensions, a striking result emerged: 0% of random combinations are physically coherent. The table's Cartesian product implies thousands of possibilities, but physics constraints eliminate nearly all of them.

Worse, the table treats every column as independent. But choosing fuel = D-T doesn't just fill one cell — it activates tritium breeding as a new design dimension, forces heavy neutron shielding, and restricts energy conversion to thermal cycles. These are cascading constraints that a flat table can't represent.

The actual design space has about 2 effective degrees of freedom: once you pick a confinement approach and a fuel cycle, most other choices are determined or heavily constrained. The table obscures this by presenting ~12 independent-looking columns.

What we need: An algorithm that takes a partial design choice (e.g., "compact tokamak with D-T fuel") and automatically derives everything that follows — with a trace showing why each consequence holds and which assumptions it depends on.

2. Variables & Domains

The design space as 8 variables, each with a finite set of possible values.

This toy problem uses a simplified fusion-like design space. Five variables are always active; three are conditionally activated — they only become relevant when certain upstream choices are made.

The conditional variables are the key insight: blanket only matters if you need to breed tritium (D-T fuel), rep_rate only matters for pulsed concepts, and magnet_type only matters if the confinement approach uses magnets. A flat table must include all three for every concept, padding the rest with N/A.

3. Constraints

12 rules encoding physics and engineering couplings.

Each constraint fires when its precondition is met, then restricts domains, activates/deactivates variables, or detects contradictions. The constraints are the reusable knowledge artifact — the same rules apply to every concept.

4. The Algorithm

Fixed-point constraint propagation: keep firing rules until nothing changes.

How It Works

  1. Initialize: every variable starts with its full domain. Apply the user's partial assignment (e.g., confinement=tokamak) by restricting those variables to singleton domains.
  2. Scan constraints: check each constraint's precondition against current domains. If a variable has been determined (singleton domain) and a constraint depends on that value, it fires.
  3. Apply effects: each fired constraint may restrict a domain (intersect with allowed values), exclude values, activate or deactivate a variable, or signal a contradiction.
  4. Repeat until no constraint produces a change (fixed point reached) or a contradiction is detected.

5. Justification Tracking

Every derived fact carries the minimal set of assumptions it depends on.

Constraint propagation tells us what follows from a set of choices. Assumption-Based Truth Maintenance (ATMS) tells us why — tracking exactly which input assumptions support each conclusion.

Minimal Justifications

Consider CompactTok (confinement=tokamak, fuel=DT, magnet_type=hts). After propagation:

neutron_shielding = heavy ← {fuel=DT}

The shielding requirement depends only on the fuel choice. It doesn't matter that we also chose tokamak or HTS magnets — any D-T concept needs heavy shielding. The ATMS records the minimal justification.

blanket = flibe ← {fuel=DT, confinement=tokamak, magnet_type=hts}

This conclusion requires all three assumptions. D-T activates the blanket variable, tokamak geometry constrains the options, and HTS magnets in compact geometry force FLiBe specifically (C11). Remove any assumption and the conclusion changes.

Why Minimality Matters

Minimal justifications enable precise transfer analysis. If two concepts share a derived fact, we can check whether they share the same justification. If yes, the conclusion transfers — it's the same reasoning in both contexts. If not, the conclusions are superficially similar but structurally different.

6. Transfer & Gap Analysis

Shared sub-problems emerge from shared justifications. Gaps emerge where propagation stops.

Transfer: Shared Derived Facts

Running the algorithm on multiple concepts reveals which engineering consequences are shared:

Shared by CompactTok, LaserDT, DTStellarator:

  • neutron_shielding = heavy ← {fuel=DT}
  • energy_conversion ∈ {thermal_steam, thermal_sco2} ← {fuel=DT}

All three are D-T concepts. Any work on neutron shielding or thermal energy conversion transfers directly between them — the justification is identical.

Gap Analysis: Novel Inputs

When we propagate from a combination not in our concept library (e.g., stellarator + DHe3), the algorithm reveals where existing knowledge runs out:

  • Determined (3): confinement, fuel, neutron_shielding — forced by inputs + constraints
  • Reduced (2): heating, magnet_type — constrained but not forced (design freedom)
  • Free (1): energy_conversion — genuinely unconstrained (gap in our rules)
  • N/A (2): blanket, rep_rate — not relevant to this concept

The "free" variables identify where we need additional domain knowledge. Energy conversion for a DHe3 stellarator is a genuine open question in the constraint set.
