## Findings

1. Figure 3 (`#figure-3`, in the Goal subsection of section 4) replaces the markdown's causal-chain bullet list rather than adding to it. The markdown (lines 172–181) has five top-level bullets and four sub-bullets tracing the discrepancy from stored energy through losses, heating, ash, wall load and cost, each a full sentence with its own framing clause and numbers. None of that list appears anywhere on the page as prose; it survives only as the diagram's short box labels, and several clauses are dropped in the process, not just compressed: "Downstream, the wall load is also impacted, which drives cost" (the framing sentence for the whole second row) has no equivalent anywhere; "so a 9 percent excess adds about 25 percent to the loss" is dropped from the Losses box; "so a shorter confinement time leaves less ash" is dropped from the Helium ash box; "sets how often the first wall is replaced" moves from the wall-load box to the Cost box, separating a clause from the sentence it originally belonged to. The render prompt's "Keep the prose" section requires carrying every list item into the page "in the same order and with the same wording," and treats new visuals as additions ("New visuals, only where they help") — not as a substitute for the list they are built from. This is the one place on the page where a new diagram stands in for markdown prose instead of alongside it.

2. Figure 2's opening line splices together two different markdown sentences and reorders them. The markdown's closing sentence for the six-area list is "`CLAUDE.md` at the root points to each area's index" (after the bulleted list, right before "**Indexes.**"). The page's Figure 2 entry box, which sits *before* the area cards, reads "`CLAUDE.md`, at the root, is the first file every session reads. It points to each area's index." The "first file every session reads" clause is not this sentence's wording — it is pulled from the directory-tree code block's annotation on `CLAUDE.md` later in the section. The original closing sentence itself never appears in its own words anywhere on the page. (Cites: "Keep the prose" — carry text "with the same wording," in order.)

3. Across the task/step/stage-strip figures (Figure 4, Figure 5, Figure 7, Figure 8), the page consistently promotes each item's lead "Findings"/"Changes"/summary sentence into the always-visible figure card and removes it from the matching collapsed `<details>`, rather than keeping it in the collapsed prose and pointing to it. The content stays visible on the page (so "a reader who opens nothing still follows the whole argument" is satisfied), but the wording is not always carried unchanged, and in a few cases something is lost rather than just moved:
   - `#round-1-task-2` (Task 2, evaluation): the entire "Findings:" sentence is gone from the detail body; it exists only as Figure 4's card text.
   - `#round-2-task-3` (Task 3, study): the markdown's first "Findings" bullet ("Most of the earlier driven points now ignite...") is absent from the detail's bullet list, which now starts at the second bullet ("The cheapest driven point moved..."); the first bullet survives only in Figure 5's card.
   - `#the-registration` (Figure 7, step 3): the markdown's lead sentence "Each kept source goes in through `scripts/source_registry.py`, which refuses to register a source without three sentences..." is dropped from the detail body and shortened in the figure card to "`source_registry.py` refuses to register a source without three sentences..." — the "Each kept source goes in through" framing is lost, not just relocated.
   - `#the-return` (Figure 7, step 4): the markdown's "This run returned `REGISTERED`: two sources registered and citable, and two candidates queued" becomes the card's "This run returned `REGISTERED` with two candidates queued" — the clause "two sources registered and citable" (which is what ties the return code to the outcome) is dropped, not carried elsewhere.
   - `#implementation` (Figure 8, Implementation stage): "The regenerated program matched the design's prediction:" is dropped from the detail body and survives only as the figure card's headline.
   (Cites: "Keep the prose" — same wording, same order; "Collapse detail, not the story" — the detail is meant to hold the lower-level material, not be the only place some of it survives while other parts move to the figure.)

4. Figure 1's alt text and caption were changed rather than kept, despite the render prompt's instruction to "Keep the markdown's alt text and caption" when redrawing a figure. The `aria-label` inserts "or independent ones in parallel" into the middle of the markdown's alt text ("...an approach, then tasks one at a time, with research and model changes..." becomes "...an approach, then tasks one at a time or independent ones in parallel, with research..."). The figcaption drops the markdown's closing sentence, "Rendered by `harness-assets/render_goal_loop.py`." Dropping the attribution is understandable — the diagram is now built in HTML/CSS, not rendered by that script — but it is still a caption change the render prompt doesn't authorize, and the aria-label change has no such rationale.

5. Bold emphasis is added to the lead clause of every item in four markdown lists that are plain (no bold) in the source: the "problems it has to solve" list and the "four kinds of thing" list in section 1, the "shape of the uncertainty" list in section 2 ("The outer loop"), and the "three further rules apply across all the areas" list in section 3. None of these are in the writer prompt's enumerated adaptations. The treatment is also inconsistent: other plain parallel lists nearby — "the goal carries" list in the loop-goal detail panel, and the "places to look" list in section 5's request detail — are left unbolded, so this doesn't read as one deliberate, uniformly applied style rule.

6. One section cross-reference is left as bare, unlinked prose: the "In the repository" evidence panel's summary line in section 3, "Directory tree of the areas above, with the goal from section 4 as the example," has no link on "section 4," while every other "section N" reference in the body (there are ten) is a working in-page link. (Cites: html.md, "Concept left for the reader to scroll for" — "Make every section reference a working link. Do not write a bare section number in prose.")

7. The inline script does more than "track navigation state." Beyond the current-section highlighting in the rail, it builds an interactive "explore" feature for Figure 1 and Figure 9: it generates chip buttons, copies DOM nodes into a live readout panel on click, toggles which elements are highlighted, and restores that state from the URL hash. The render prompt's hard constraints say "An inline script may only track navigation state, as the style sample's script does." The page reads fine with scripts disabled (the explore panels stay `hidden` and the equivalent prose sits in ordinary, always-readable `<details data-fallback>` blocks instead), so the no-script requirement is met, but the script's scope looks broader than the literal constraint describes. I have not read the style sample, so I can't confirm whether this explore behavior is already established there as within-spec.

8. New text the page adds in Figure 7's step 2 card — "It kept a 2021 paper and a 2023 thesis, rejected four candidates and queued two for a person" — names the kept sources but reduces the rejected and queued items to bare counts. The full names (the publisher's page, two Proxima Fusion pages, the Helios paper; the author query and the confinement-scaling paper) are one click away in `#the-search`, but the visible summary itself doesn't name them. (Cites: synthesis.md, "Count standing in for the members" — "Name the members. If you give only a count, the reader still has to ask which ones you mean.")

9. Four `<details>` summary lines invented by the page — "Spec: all 15 requirements" (`#spec`), "Design: stored energy by machine size" (`#design`), "Plan: what the account says about each study" (`#plan`), and "Implementation: the code, and how it was checked" (`#implementation`) — are colon-joined double clauses, one with a count. The markdown gives these sections only a plain bold run-in label ("**Spec.**", "**Design.**", "**Plan.**", "**Implementation.**"), so the elaborated summary text is the page's own addition, not carried text. (Cites: html.md, "Dropdown summary line written as a double clause" — "Write a summary line the way you write a heading: a bare noun phrase, or one dead-simple claim. Bad: colon-joined double clauses and counts in the summary lines.") By contrast, the task/step summaries that quote markdown's own subheadings verbatim (e.g. "Task 1, research: how does the paper define stored energy?") are carried text, not new summaries, and aren't part of this finding.
