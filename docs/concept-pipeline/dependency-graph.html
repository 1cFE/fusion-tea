1. End-to-end overview

The library has two parallel downstream pipelines that share early artifacts and diverge at the end. Concept Explorer is the per-concept deep-dive UI. Score Explorer is the cross-concept downselect UI. They draw from overlapping but distinct artifact sets.

State is derived from filesystem by lib/state.py:get_concept_state(). Staleness propagates via propagate_staleness() when analysis.md mutates — marking model_setup.py, review.md, and synthesis.md with # STALE: / Stale: true.

Note on synthesis.md: the synthesis is a terminal artifact — a colored editorial interpretation of the analysis (executive summary, what matters for LCOE, risk verdicts, cross-concept positioning, modeling confidence, what would change my mind). It is read by humans only; no downstream automation consumes it.

What the consumers actually read

ConsumerReadsIgnores
extract_explorer_data.py module.result (or result_1gw if defined) + model.sensitivity(result.params) result_foak, result_steam, result_ohmic, freeform scenarios — never accessed
scoring_v2/lib/extractors/cost_model.py Regex-parses CAS code lines in model_output.txt. Only the nominal block prints full CAS dumps by convention. Alternate-scenario summary lines (LCOE: ... | Overnight: ...) don't match the regex.
LLM stages (assess / review / synthesize / next-iter analyze) Whole-file text of model_output.txt as narrative context — sees the scenario tables and may cite them in prose. No structured extraction.

So: only the nominal case feeds scoring and the Concept Explorer. Non-nominal cases exist purely for the analyst and for LLM-stage narrative context.

7. Cross-cutting fragility

1. synthesis.md is editorial-only and has no downstream consumer. Neither scoring_v2 nor the Concept Explorer reads it. The synthesis prompt is intentionally a colored interpretation document — voice, framing, cross-concept positioning. Producing it is pure analyst-facing output; no automated pipeline depends on it.
2. gap_report.md is a quiet upstream of downselect. It isn't read by the analysis loop after gap-check completes, but scoring_v2/scripts/populate_data_availability.py reads it to score the Data Availability axis. Regenerating gap reports ⇒ must re-run populate ⇒ re-score ⇒ rebuild explorer JSON.
3. docs/score-explorer/ is a manual mirror of tools/score_explorer/. No script ties them — a chore commit copies them (e.g. 33bde4f). Easy to forget after build.py runs; the GitHub Pages site will silently lag.
4. model_output.txt feeds two independent consumers. Concept Explorer extractor and scoring_v2 cost-model extractor both read it. Re-running model-setup invalidates both — but only the .stale markers on Concept Explorer JSON are tracked automatically.
5. concept_analysis/table.csv is taxonomy ground truth referenced twice. Both scoring_v2/extract.py and tools/score_explorer/build.py use it. Orphan concepts — analyses/ dir present, no row in table.csv (e.g. 34-compact-spherical-tokamak-india) — fall out silently.
6. Scoring v2 CAS-line parser would silently double-count an alt-scenario CAS dump. scoring_v2/lib/extractors/cost_model.py:_parse_lines sums every CAS-code line in model_output.txt. The current "alt scenarios print summary lines only" convention is what protects us — there is no delimiter, no header check, and no duplicate-code detection. If a future model_setup.py author prints a full CAS breakdown for a FOAK result, the subsystem weights inflate proportionally without warning.
7. result_1gw is a silent override in the Concept Explorer. extract_explorer_data.py:262 replaces result with result_1gw whenever the module defines both. Today this is used for per-account 1-GWe normalization (concepts 20a, 29, 34), not as a scenario, but nothing in code enforces that distinction. No frontmatter flag, no warning if a future author uses result_1gw to hold an actual alt-scenario.
