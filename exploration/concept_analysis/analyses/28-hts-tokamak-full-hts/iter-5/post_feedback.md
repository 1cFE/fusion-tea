### F-1: Interest rate sweep recommended but not executed
- **Target:** Section 2 (Key LCOE sensitivity parameters, item 2) and model output
- **Category:** model
- **Finding:** The analysis explicitly states that cost of capital / interest rate "should be the axis for scenario sweeps" and labels it the "primary financial lever." The model sensitivity confirms this is the second-highest elasticity parameter (+0.6561), ahead of thermal efficiency and construction time. However, the model output includes no interest rate sweep table. The two sweep tables present (hts_full_coil_premium and structure/vessel thickness) address parameters with far lower LCOE leverage. The analysis makes a specific methodological recommendation — sweep interest rate — that the model does not carry out.
- **Recommendation:** Add an interest rate sensitivity table to the model output sweeping across a plausible range (e.g., 5%, 7%, 9%, 12%) and report the LCOE at each step alongside the base case. Frame it as bracketing the financing-cost uncertainty that is structurally inseparable from the absent commercial design anchor. This is the highest-priority missing sweep given the analysis's own stated rationale.
- **Priority:** important

### F-2: Disruption model treatment undocumented
- **Target:** Section 2 (Challenge #4 — AI plasma control) and model sensitivity table
- **Category:** model
- **Finding:** AI plasma control as a disruption-frequency reducer is framed as the primary novel differentiator (Challenge #4) and one of the two technical bets modeled as scenario branches. The model sensitivity table lists four disruption parameters (`disruption_rate_base`, `disruption_steepness`, `disruption_damage`, `disruption_downtime`) all showing 0.0000 elasticity. These parameters are zero-valued in the base case, which means perturbing them by a percentage of zero yields zero LCOE change — their zero elasticity is a mathematical consequence of zero base values, not a sign they are disconnected. The actual disruption risk is captured through the availability scenarios (A: 65%, B: 70% vs. base 85%), which is a defensible modeling choice. However, neither the analysis nor the model output documents this choice: why disruption is modeled through availability scenarios rather than through disruption cost parameters, and why the base case sets all disruption parameters to zero. A future reader seeing these parameters at zero elasticity will reasonably conclude the disruption model is incomplete.
- **Recommendation:** Add a brief note in the model output (under Key Assumptions or a new "Disruption Model" block) stating explicitly: base-case disruption costs are set to zero; disruption risk is fully captured through the availability scenario branches (A and B), making the disruption-parameter rows in the sensitivity table intentionally inert. Optionally, add a comment in the analysis (Section 2, Challenge #4) cross-referencing this modeling choice so the narrative and model are consistent.
- **Priority:** minor

### F-3: Modeling framework choice not stated
- **Target:** Section 2 (Modeling Recommendations)
- **Category:** analysis
- **Finding:** The assessment checklist requires the analysis to state whether 1costingfe or free-form modeling is appropriate and why. The model output header identifies this as a "Proxy model: CFS ARC/SPARC analogue" using the 1costingfe CAS10–90 framework with defaults from steady_state_tokamak.yaml, but the analysis text contains no explicit statement of this choice or the reasoning behind it. For a concept rated LIMITED with no commercial design parameters, the choice to use the 1costingfe framework with proxy parameters (rather than a free-form model) is non-obvious and worth stating: it enables direct cross-concept LCOE comparison at the cost of anchoring an entirely undisclosed design to CFS ARC/SPARC assumptions, carrying stated ±50% or greater uncertainty.
- **Recommendation:** Add a sentence or short paragraph in Section 2 (near the scenario structure discussion) stating the framework choice explicitly: "This concept uses the 1costingfe framework with parameters proxied from CFS ARC/SPARC (Sorbom 2015) and steady_state_tokamak.yaml defaults, because no commercial design point exists for HH380. Free-form modeling would not reduce uncertainty given the complete absence of disclosed engineering parameters, while the framework approach enables apples-to-apples comparison with other MFE tokamak concepts in the analysis pipeline."
- **Priority:** minor
