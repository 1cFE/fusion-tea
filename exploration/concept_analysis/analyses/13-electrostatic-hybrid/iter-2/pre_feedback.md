### F-1: P_native drift between design point and model creates incoherent framing
- **Target:** Design Point block (analysis.md top-of-body) and model_setup.py P_native constant
- **Category:** analysis
- **Finding:** The Design Point block states `P_native: 0.005 MWe` (5 kWe), but the model_setup.py sets `P_native = 1.0` (1 MWe) — a 200× discrepancy. The analysis extensively documents the workaround justification (Section 2 Challenge 1, Section 5 inference chain, the analyst-patch source) but never revises the top-of-body Design Point block to acknowledge that the modeled artifact is **not** the nominal 5 kWe design point. The Section 5 parameter table carries the 5 kWe framing throughout ("5.0 MWe" in row 1, despite that being a typo for 0.005 MWe), while the model silently operates on a different machine. This violates design-point coherence: the analysis must describe the plant the model prices, not a different one.
- **Recommendation:** Add a "Modeling Workaround" subsection immediately after the Design Point block explaining that the library cannot converge below ~1 MWe (reference Section 2 Challenge 1), so **the model prices a 1 MWe module** and the 1 GWe headline reflects 1000× replication of that artifact, not 200,000× replication of a 5 kWe device. Revise the Section 5 parameter table row 1 to read `1.0 MWe (library convergence floor; actual Avalanche target 0.005–0.100 MWe)` and add a note clarifying that all subsequent parameters describe the **1 MWe modeled artifact**, not the 5 kWe nominal design point, where they differ. The analysis already contains the substance of this fix (Challenge 1, the model header, and the analyst-patch source all explain the issue); it just needs to be surfaced in the Design Point block so the reader isn't surprised by the model drift.
- **Priority:** blocking

### F-2: Override count (0) below Med-fit band (3–8) without explicit justification in Section 5b
- **Target:** Section 5b (Override Candidates)
- **Category:** analysis
- **Finding:** The concept is graded Med archetype-fit (expected 3–8 enabled overrides), but Section 5b registers zero overrides with the rationale "The per-account walkthrough identified no company-grounded cost data." However, Section 5b does **not** include a per-account walkthrough — it jumps directly from the fuel-ambiguity blocker to `overrides: []`. A Med-fit concept means the library's default story is a **poorer** match than for a High-fit concept, so trusting the library on all accounts is inconsistent with the grade unless the analysis explicitly walks through the CAS accounts the archetype touches and explains why each default is acceptable despite the poorer fit. The analysis documents extensive subsystem-level detail (Section 3 maturity, Section 4 supply chain), but that knowledge never routes to override-candidate evaluation.
- **Recommendation:** Add a per-account walkthrough subsection before the YAML block. For each CAS account the ORBITRON archetype touches (at minimum: C220101 blanket, C220102 first wall, CAS21 structures/site, CAS23 turbine plant, CAS24 electric plant, CAS25 misc plant, CAS26 heat rejection), state whether the library default is appropriate for this design point or whether a departure is justified. If no company-published cost data exists to justify an override (the likely outcome, given the opaque data rating), **say so explicitly per account** — "C220101 (blanket): no override; Avalanche has not published blanket cost, and the library's molten-salt FLiBe default is a reasonable proxy for a heat-exchange-only vessel at this scale." This walkthrough will either surface legitimate override candidates (raising the count into the 3–8 band) or document why the zero-override outcome is defensible despite Med fit. The current Section 5b leaves the reader uncertain whether the zero count reflects actual data scarcity or incomplete analysis.
- **Priority:** important
